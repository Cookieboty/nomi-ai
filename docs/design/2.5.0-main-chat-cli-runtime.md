## 0. 目标与约束

**目标**：同一产品会话（同一侧栏项、`ChatSession.id`）内，即使没有模型供应商也能直接使用本机已登录的 Claude Code，再切到 Codex，再切回 Claude；切回时恢复该 CLI 自己的原生会话并只补离开期间的增量；恢复不了才新建并做有界全量文本交接。全程单一权威历史。

**硬约束**（评审后仍成立）：

1. 现有 API（Nomi 网关）运行时可用；但其**持久化与执行接入**随单一权威切换（§5），不能声称「API 运行时不变 = 持久化不变」。
2. 统一运行时原语：`send / stream / cancel / approval / capabilities / recovery-result`。
3. CLI 自己拥有 agent loop 与工具执行；不伪造原生工具 / 推理历史。
4. 只用官方 CLI 接口与本机登录；不读、不存、不刷新、不搬运凭据，不检查 token。
5. 单一权威转录、内核单写者、不做无事务双写；**不限定必须新建日志**。存储落点是设计决定（§2），不是用户硬约束。
6. 空闲才可切换；切换是持久事务；每次发送有独立的持久阶段。
7. 切换不改工作区文件。
8. 迁移无损、可恢复、确定（不按条数猜）。
9. 原生 MCP / skills / 记忆 / 知识库不共享，能力缺失显式降级。

**不满足目标的做法**（不采纳）：仅在标签栏加后端下拉；把任务转交 Agent 标签 / 分叉会话；研究稿 §4「同标签切后端 + 每次新建 + 截断前文」的最小版。

**范围限制（本文不承担）**：不做流式中 / 审批中 / 后台工具运行中切换；不迁移推理、工具现场、审批、子代理、历史图片；不做文件检查点或切换回滚；`dsh` 在 B1–B3 早期阶段暂不纳入，后续已在受限只读 headless 路径接入，见 §18。

## 2. 设计的决定性选择

**决定 S1（B1 评审后记录，B2 的实现方向）**：优先**扩展现有内核 convstore**，由会话级内核服务作为唯一命令入口；`conversationruntime` 仅保存存储无关的模型、预算与覆盖算法。**不再要求将 convstore 降为另一份新权威日志的镜像**。

| 对比     | 扩展 convstore（选择）                                                                | 独立 runtime 日志 + convstore 镜像（不选择）            |
| -------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 现有基础 | `store.go` 已有单锁、原子整份替换、JSONL 读取、索引恢复、导入及坏尾行测试             | 需重建这些能力，并维护另一份投影与游标                  |
| 数据迁移 | 同一存储服务内按会话升级，旧原始字节保留；读 API 可在服务内投影                       | 搬至新目录、镜像一致性、旧入口截断与双侧恢复同时发生    |
| 单写者   | 仍需把 `shellhandlers`/视图/API 完成路径改为类型化命令；现有锁**不等于**已解决所有权  | 同样必须改全部 ingress；新增包本身不能阻止第二写者      |
| 原子性   | 需要新版本提交单元，把消息修订与绑定/attempt 一起提交；不能裸写 messages 再写 sidecar | journal 需 commit/checksum、fsync、重放、压缩与投影游标 |
| API 集成 | 保留 conversations 的读取与侧栏 id，托管会话的旧写命令仍必须封闭                      | 新查询路径或镜像读取，加一层投影失败状态                |
| 主要代价 | 当前正文是 opaque RawMessage，必须保留未知字段；原子整份提交的大会话性能需测          | 运维/恢复面更大；暂无证据证明双格式更省事               |

**证据与限制**：`convstore.Store`（store.go 的包注释、Store、Put/Append/Replace/Import）及 `shellhandlers/conversations.go` 的 `InstallConversations` 表明已有存储边界可扩展，但当前 v1 并无类型化 revision、绑定、尝试事务，也会整份替换。选择复用服务**不声称**现格式已经满足要求。B2 首个隔离 fixture 切口验证**一个版本化提交单元原子保存正文+运行时状态**（优先每会话原子快照，保留修订；索引只派生），包含失败注入、重启和未知字段 round-trip；若大会话写放大不可接受，再在同一 convstore 服务内评审 journal，不能暗自增加第二权威。

**未发生任何 userData 切换**。S1 选定服务归属与单写者边界；具体磁盘 schema/容量阈值仍须 B2 fixtures 通过后批准，不把下述逻辑 commit 示例当成已批准磁盘格式。原新 runtime 目录方案撤回；harness 保留普通 Agent 标签语义，会话级 CLI 不经全局主槽。

## 3. 数据模型（Proposal；Go 侧 struct PascalCase + `json:"lowerCamel"`）

### 3.1 条目 `RuntimeEntry`（稳定逻辑 ID + 追加修订）

```jsonc
{
  "id": "m_01J…",              // 稳定逻辑消息 ID：修订之间不变
  "revision": 1,               // 从 1 起；同一逻辑消息每次修改 +1
  "order": 7,                  // 首次写入时分配；永不修改、永不重排（墓碑也不挪）
  "turnId": "t_01J…",
  "attempt": 0,                // 观测字段：同一 turn 的第几次发送尝试
  "origin": {
    "kind": "user" | "assistant" | "system",
    "runtime": "api" | "cli",
    "cli": "claude" | "codex" | "gemini" | "grok" | null,
    "bindingId": "nb_…" | null,
    "nativeSessionId": "s_…" | null,
    "source": "local" | "official" | "thirdParty" | null,
    "accountId": "…" | null,
    "model": "…" | null
  },
  "role": "user" | "assistant",
  "content": { "kind": "text", "text": "…" },
  "attachments": [ { "kind": "image", "ref": "asset:…" } ],   // 只声明，不进交接正文
  "flags": { "error": false, "stopped": false, "tombstone": false },
  "legacy": { /* 迁移前的未知键原样 */ },
  "createdAt": 0
}
```

不变量：

- **逻辑消息 ID 跨修订不变**：编辑只追加 `(id, revision=k+1)` 的记录；旧修订保持可读。
- **`(id, revision)` 在会话内唯一**；日志写入端拒绝重复键。
- **`order` 不可变**：分配后不重排；**墓碑不改 order**，只在 `flags.tombstone` 置位并保留可读原文供审计与旧镜像。
- 编辑器（`edit`/`rewind`）产生新修订而非覆盖；视图按书签语义只显示最新非墓碑修订，历史修订保留在日志。
- `origin` 必填；迁移条目 `runtime` 按来源推断，但 `bindingId` 只有「确定的旧原生会话」才填（§10）。

### 3.2 原生绑定 `NativeBinding`：`bindingId` 按原生身份稳定

- `bindingId` 对一个**原生会话身份**稳定：同一物理原生会话（重开同进程、切回同一配置）沿用同一 `bindingId`；
- `attempt` / `generation` 是**发送尝试与代次计数**，归属放在 `AttemptRecord` 与 `SwitchTxn`，**不混进** `bindingId`。

```jsonc
{
  "bindingId": "nb_…",                       // 稳定
  "nativeSessionId": "s_…",
  "compatibilityKey": "k2:…",                // 见 §3.3，可在多个配置间比对
  "driver": { "id": "codex", "transport": "app-server", "version": "0.43.1", "supportsResume": true },
  "cli": "codex", "source": "local", "accountId": null,
  "exe": { "path": "/usr/local/bin/codex", "realpath": "/opt/…/codex", "size": 123456, "mtimeMs": 0 },
  "configDirId": "cd_…",                     // 不存路径明文外的秘密；见 §3.4
  "configGeneration": 7,                     // 非秘密配置代际（目录 watch 计数 / 配置文件 mtime 合成）
  "launchFingerprint": "lf_…",               // 启动参数敏感项摘要（§3.4）
  "cwd": "/abs/project", "extraDirs": ["/abs/x"], "extraDirsCanon": "posix" | "win-volume",
  "model": "…", "effort": "…", "permissionMode": "…",
  "status": "live" | "idle" | "stale" | "unknown" | "unverified",
  "coverage": { "delivered": { "m_a": 3 }, "handoff": { "m_c": 2 },
                "partial": { "m_b": { "revision": 1, "digest": "…", "unit": "utf8", "ranges": [ { "start": 0, "end": 613 } ] } },
                "omitted": [ { "id": "m_d", "revision": 1, "reason": "budget" | "attachment" | "error" | "tombstone" } ] },
  "createdAt": 0, "lastUsedAt": 0
}
```

**`bindingId` 稳定 + 旧绑定保留（评审项 1）**：改配置、换账号、升级驱动都会产生**新**绑定，但旧绑定**不删**，以它自己的 `compatibilityKey` 与 `nativeSessionId` 留在「绑定兼容索引」中；切回旧配置且配置代际未变 → 仍可尝试恢复旧绑定（结果按 §7.2 判定），旧绑定与新绑定并行存在。

### 3.3 `compatibilityKey`（确定性摘要，非安全哈希；不接触凭据）

```text
compatKey = sha256hex( join("\x1f", [
  "schema=2",
  driver.id, driver.transport, driver.version,            # 版本兼容：驱动层解析器已知可恢复的版本区间
  driver.resumeProtocol,                                  # e.g. claude:argv-resume ; codex:thread/resume ; acp:session/load
  exe.realpath, exe.size, exe.mtimeMs,                    # 解析后的可执行文件
  launchFingerprint,                                      # §3.4 启动参数敏感项
  source, accountId ?? "",                                # 账号来源与 id
  configDirId, configGeneration,                          # 配置目录身份 + 代际（不含秘密）
  cwdRealpath, extraDirsCanon, extraDirsCanonicalized     # OS 敏感规范化
]))
```

- **必须包含**：driver / transport / 驱动版本 / resume 协议；解析后的可执行文件（`realpath` + 大小 + mtime）；启动 argv 敏感项（§3.4）；配置目录身份与非秘密配置代际；`source` 与 `accountId`；`cwd` 与额外目录的规范化形式。
- **不得包含**：任何 token、OAuth 字段、凭据文件内容或哈希。配置目录「身份」= 路径 + 卷标识（Windows）+ 目录 inode/`FileId`（Unix，取不到则退化为创建时间）；**代际**由非秘密配置文件的集合 mtime/大小合成，或配置目录 `fsnotify` 事件计数，稳定取不到则 `unknown`（`unknown` ≠ 匹配）。
- **同一 `source` 但配置 / 账号变了**：新 `compatKey` 与旧绑定不同 → 旧绑定标 `stale`（或 `unknown`，若配置代际读不到），**不**在旧绑定上继续；新发送按 `new` + 有界 full。
- **权限 / 模型 / 思考深度**：恢复兼容性**按驱动查表**（§3.5），而不是「清单 `modelSwitch: inplace` ⇒ 可原生恢复」。`inplace` 只说明「可换模型」，不保证换模型后原生会话可续。
- **额外目录的规范化按 OS**：Unix 用 `realpath` + 保留大小写；macOS 额外做 NFC 归一与 HFS 大小写不敏感探针；Windows 用 `GetFinalPathNameByHandle` 形态（`\\?\` 前缀、卷序列号、大小写归一到小写）；跨卷 `..` 先用平台 API 解析再入摘要。`extraDirsCanon` 记录所用规范化版本，规范化版本升级时旧绑定按 `stale` 处理，不静默重算。

### 3.4 `launchFingerprint`（启动参数敏感项）

该摘要只覆盖**非秘密**启动参数：CLI 可执行解析结果、合并后的启动 argv 中影响 session 恢复的项（如 Claude 的 `--append-system-prompt`、沙箱参数、MCP 启动参数中影响会话的开关；Codex 的 `-c` 中影响 sandbox/approval 的键）；`source` 决定的配置目录注入（`CLAUDE_CONFIG_DIR` / `CODEX_HOME` 是否存在及其身份）。凭据类环境变量**一律不入摘要**，也不读取。

## 4. 覆盖率账本（覆盖语义，评审项 2）

### 4.1 覆盖率 = 显式覆盖，不接受「最高 order / 最高 ID 水位」

`needsDelta(binding, entries)`：

```text
for e in entries where !e.flags.tombstone, ordered by e.order:
    if coverage.delivered[e.id] == e.revision:      continue       # 全条目已体现
    if coverage.handoff[e.id]   == e.revision:      continue       # 经交接正文已体现
    if coverage.partial[e.id].revision == e.revision
       and coverage.partial[e.id].digest == digest(e)          # 同一 revision 的规范化文本
       and liberalCover(coverage.partial[e.id], e):            # union(已知区间) 覆盖全文
        continue                                               # → 视为 full；否则按 partial 继续算候选
        # 已知区间未覆盖全文 → 剩余部分仍是候选（resume-partial），不得写成 delivered
    unread += classify(e)   # new | edited(revision>已见) | resume-partial | omitted(reason)
```

- **部分投递 ≠ 全量覆盖**：一条被 4000 字符截断的消息，只能记 `partial{revision, digest, unit, ranges}`。`ranges` 是**规范化后的显式偏移区间**（半开 `[start,end)`），`unit` 固定 `utf8`（备选 `utf16`，同一绑定内不得混用）；规范化 = NFC + `\r\n`→`\n`；`digest` 为该 revision 规范化文本的 SHA-256。只有 `union(ranges)` 覆盖全文（「liberal cover」：JSON / quote 包裹造成的重叠允许）才视为 full；否则未覆盖区间仍是候选，不得写成 `delivered`。
- **省略不是吸收**：`omitted` 只表示「这一轮因预算没带」，**不是永久 marker-only**。每次交接重新计算：候选 = 未全量覆盖的条目 + `omitted` 中「若预算允许可带」的条目；只带得下时优先按 §7.3 顺序补带（回填 / 重选）。只在仍未带上时，这一轮才输出简要省略说明。
- **编辑 / 回退使受影响绑定全部失效**（评审项 2 的硬要求）：条目 `id` 被编辑到 `revision>k`，所有把该 `id` 的旧 revision 记为 `delivered` / `handoff` / `partial` 的绑定立即 `stale`——**除非**该绑定能通过**真实的原生回退**（Claude `--resume-session-at` / Codex `thread` revert）回退到与目标 revision **一致**的原生状态，并由驱动回执确认；仅发「文本已修订」通知**不算**恢复，内部状态已不一致。
- **对未编辑条目的部分覆盖**：仍保留 `partial` 并在下一次补正文。

## 5. 单一权威：写入者、提交点、镜像（评审项 6）

### 5.1 存储归属（S1；B2a 基础与 B2b 显式接线已实现）

沿用 `<userData>/conversations/` 的 convstore 服务与读接口。v1 的 `messages/<id>.jsonl`、原始未知字段及损坏行均保留备份，不原地套用本文 Entry 结构。B2 只在临时 fixture 目录实现版本化托管提交单元，**不**建立第二套 `<userData>/runtime/` 权威。

正文修订、绑定、coverage、attempt 与切换状态必须共享一个原子提交点；不能因为复用 convstore 就允许正文文件 + 状态 sidecar 顺次双写。索引/预览/视图 DTO 是派生读模型，可以重建，不能反过来覆盖权威。具体磁盘 schema 是 B2 的待验收项。

### 5.2 逻辑原子提交记录（不是已定的磁盘格式）

每个需要原子性的变更（一轮完成的 assistant + 覆盖 + 绑定状态 + 可选 txn 迁移）打包成一条记录：

```jsonc
{
  "kind": "commit",
  "commitId": "cm_…",
  "conversationId": "c_…",
  "seq": 42, // 单调的逻辑提交版本；不绑定物理 journal 格式
  "batch": [/* entry / revision / coverage / binding / txn 记录，按序应用 */],
  "checksum": "sha256hex(规范序列化的 batch + seq + prevChecksum)",
  "prevChecksum": "…",
  "committedAt": 0,
}
```

- 上述记录表达逻辑原子性，**不要求新建 append-only journal**。B2 优先验证同一 convstore 内每会话版本化原子提交单元；临时文件完整写入、flush/fsync、原子替换及目录持久化失败必须注入测试，不能把一次 `Write` 视为崩溃原子。
- 若以后选择 journal，才另行实现完整批次的 checksum/commit、短写检测、坏尾部隔离、重放与压缩；不得提前声称这些已存在。
- 读取投影、索引、预览不在权威提交内；投影更新失败不回写正文，恢复时按权威版本重建。**不再把整个 convstore 当作独立镜像**。

### 5.3 单一写入者与旧入口改写（cutover）

- **会话内核服务是托管 convstore 的唯一命令入口**（存储锁、文件锁与尝试所有权共同约束；`shellhandlers` 不再绕过类型化命令裸写托管正文）。
- **托管会话**（有已提交 v2 所有权记录的会话）：`conversations.put / append / replace / delete / pointers` **全部拒绝**（`CONVERSATION_AUTHORITY_MANAGED`），**无例外、无 `AppendMirrorEntry` 之类的替代写入**——任何由视图触发的正文写都会变成第二写者或绕过 authority 提交。镜像 / 投影**只由内核私有投影器**从权威提交写出。旧视图写入必须先适配到 `conversationRuntime.*`，在此之前不做真实切换（§12 B2 门禁）。
- **视图 ingress 全部重定向**：`IPCClient.saveMessageTo / saveMessage / saveMessageAfterTo`（F2）以及 `userMessageSaver`（`chatTurn.ts` L154–174）在托管会话上走 `conversationRuntime.ingestUserMessage` / `recordAssistant`，不在视图侧 `store.upsert` 直接改消息；`store` 保留为读缓存（从镜像与事件刷新）。
- **API 运行时也写权威**：API 路径在 `ipcClient.sendMessage` 调用前后：视图只带 `requestId`；内核 `beginTurn` **预留 attempt 并签发所有权 token**（`ownershipToken`），`completeTurn` 必须携带同一 token 才能写 assistant 条目与覆盖（`runtime:api`）；内核按 `(conversationId, requestId)` 幂等预留，**同一完成只 ingest 一次**，重复或 token 不符的 `completeTurn` 被拒绝。因此 **API 运行时的持久化也切到权威**；「API 运行时不变」只指**协议与网关执行**不变，持久化路径改变必须在此写明。
- **多窗口**：窗口只发「意图」，由内核统一排队（发送、编辑、删除、切换在同一 `runtime.Store` 锁内按 `conversationId` 串行）；**排队也是内核状态**（`pendingSends` 从视图迁到内核 `queue` 记录），视图排队字段在 cutover 后只做展示。

## 6. 发送尝试：独立持久阶段（评审项 5）

每次「用户点击发送」产生 `AttemptRecord`，与切换 txn **分离**（切换 txn 见 §8）。

```text
planned       写 user 条目（一次）+ attempt 记录（含 turnId / attempt / 选中的交接集合）→ fsync
dispatching   写「即将写入 CLI」标记 → fsync → 然后才向 CLI 写第一字节
accepted      CLI 以官方事件确认接受了本轮（turn/step 开始）
completed     产出 assistant 条目 + 覆盖推进（与 commit 原子）
uncertain     写入后到 accepted 前崩溃 / 超时 / 取消未收到回执
failed        官方明确的 pre-submit 失败（未写入 CLI 即失败）
```

- **fsync 先于任何 CLI 写入**：`planned` 记录中的 user 条目与 attempt 必须先落盘并 fsync（§5.2 的 commit 记录），之后才允许 spawn / 写 stdin。
- **`uncertain` 不自动重放**（评审项 4）：下一次发送 / 启动恢复时只能**等待用户显式选择**（「重试 / 放弃」）；重试复用同一逻辑 user 条目（`turnId` + `attempt+1`），**不**再追加第二条 user。
- **取消**：`cancel` 使当前 attempt 进入 `cancelled` 并递增 `cancelEpoch`；`cancelEpoch` 对迟到的 `accepted` / 文本事件一律拒绝（§9.3）。
- **不把旧历史当作独立的可执行用户请求发送**：交接文本只作为带归属的有界上下文，**置于本次用户请求之前**（模板见 §7.4），切换流程本身**从不**触发 CLI 回合。

## 7. 交接（Handoff）与恢复（Resume）

### 7.1 候选集合

```text
prior = { e | !tombstone(e) } - { e | e.turnId == currentTurn && e.id == currentUserMessageId }
                                                      # 本次请求排除（评审项 3）
fullCandidates  = prior                               # 与旧绑定覆盖无关；new / fallback 从空覆盖开始
deltaCandidates = prior - { e | fullyCovered(binding, e) }   # 只去掉完全已覆盖的条目
full  = 在 fullCandidates（整段先前历史）上按预算做有界选择
delta = 在 deltaCandidates（未完全覆盖 / partial / edited）上按预算做有界选择
```

- 本次用户请求（按 `turnId` 与逻辑 `id` 双条件）从 selected 中**排除**；交接只包含更早历史。
- `full` 是「全部 eligible 历史的有界选择」，包含首次请求（若它仍未覆盖）；`delta` 候选只有未覆盖项。
- **轮次内插入消息**（`upsertAfter` / 插队）如果已成为历史条目且未覆盖，按普通候选处理；正在发送中的这条不入候选。

### 7.2 恢复判定 `ResumeOutcome`

```text
recover(binding):
  if binding == null → new(no_binding)
  if binding.status == "unverified"（迁移来的、证据不足）
        → 能力门控：该驱动须具备「已证明的官方、无提示安全握手」才允许探测
           · 不具备 / 未知 → 不探测；保留旧 binding，本轮计划显式 new + full（不假装 resume）
        → 具备时做一次「安全恢复探测」：只 resume、不发送任何用户内容，读官方事件确认身份
           · 身份一致 → resumed
           · 明确失败（驱动的 pre-submit 错误 / session 不存在）→ new(needs_full)
           · 超时 / 无回执 → unknown（不提问，保持 unverified）；此后重启 / 下次发送**不静默重试**探测，等待用户显式决定
  if binding.status == "unknown"（上次执行结果不确定）
        → 阻塞：需要用户显式决定（重试 / 放弃 / 新建），CANNOT 自动 new，CANNOT 发送
  if binding.compatKey != current.compatKey → stale → new(needs_full)（旧绑定保留）
  if 驱动 resume 结果：
        · resumed:true 且 nativeSessionId 一致 → resumed
        · 明确 pre-submit 失败 → new / fallback(full)——只有「明确未提交」才允许回退新建
        · 其它（超时、进程崩溃、无回执）→ unknown（不自动重放）
  Claude：argv 带 --resume 只是「意图」；必须由官方事件中的 session 身份等于绑定才确认 resumed，
          否则 unknown（不能按 argv 假定成功）
```

### 7.3 有界选择（预算语义）

- 选择顺序：① 首条 user（**delta**：仅当它属于 `deltaCandidates` 且未被覆盖；**full**：永远属于 `fullCandidates`，按预算处理）；② 最近问答对（user+assistant 成对，不成对则不选）；③ `edited` / `partial` 补全；④ `omitted` 回填。
- 单条、单轮预算按**传输编码**分别计量（§7.5），不复用研究稿「40 条 / 4000 / 60k」作为最终值；数值待定但**必须**满足总预算并保留本次请求（§7.5）。
- **空预算不消费交接**：若选完后交接正文为空（预算不足一条最小单位或全部排除），本轮不写 `pendingHandoff`、不推进覆盖，`recovery-result.handoff = {strategy:"none"}`。
- **失败重试同一集合**：一次交接的 `selected(id:revision)` 写入 `pendingHandoff`；失败（含 `FitCarried` 类裁剪为空）**保留** pending，下次仍用同一集合；成功且被 CLI 接受后才推进覆盖。
- 「裁剪为空」不等同「历史已交付」；仅在裁剪成功且回合被接受时更新 `delivered` / `handoff` / `partial`。

### 7.4 交付形态（属前言，不构成独立用户任务）

```text
<conversation_handoff note="bounded prior context, not a new request">
[user] …                      # 历史条目，带归属
[assistant/claude] …
[omitted: 12 entries due to budget]
</conversation_handoff>

---

<本次用户请求原文，原样>
```

- 新 i18n key（zh/en + Go 副本），**不再**使用「工作目录已经换成当前目录」的旧文案。
- 正文只含 `content.text`；不含工具、推理、审批、图片、`memory` / `sources` / `steps`。图片作为历史附件在 `omitted(reason:attachment)` 列明。
- 恢复成功时若 delta 为空：**不注入前言**，本次请求原样发送。

### 7.5 请求上限：执行前拒绝，绝不静默截断；总量预算

- **移除对 `SendTab` L52 100k 截断的依赖**；运行时在 spawn 前计算：
  ```text
  total = argvBytes + overheadBytes(transport) + requestBytes(transport) + handoffBytes(transport) + reserveBytes
  ```
  - **三类度量分开、各判各的**：① **逻辑文本**预算保留 **UTF-16 码元**度量（仅用于旧版 / 兼容数值比较）；② **序列化载荷**（Claude `stream-json`、Codex app-server JSON-RPC）经 **stdin** 传输，上限按**序列化后的 UTF-8 字节**计（含 JSON 转义 `\uXXXX`、引号、分隔符）；③ **Windows 命令行**只约束 argv，按 **UTF-16 码元**计，**不**适用于 stdin。
  - **各限额分别满足，不跨单位相加**：stdin 序列化字节、命令行码元、逻辑文本码元各自独立判定；不同单位的数值不得相加成「总预算」。
  - 测试覆盖中文 / emoji / JSON 转义（emoji 被转义后序列化字节增大；中文 UTF-16=1、UTF-8=3）。
- 若「本次请求 + 不可省略 overhead」超出上限 → **发送前拒绝**并返回可操作错误（提示分段发送 / 缩短），**不截断**。
- 若仅交接超限 → 从头部裁剪交接（记录 `omitted`），**保留本次请求**。
- 每驱动上限值在 B1 只建表与算法，实际数值在 B3 用假 CLI 与文档化 CLI 限制校准，未验证值标注为「暂定」。

### 7.6 Claude 恢复确认

Claude 的 argv `--resume` 只产生「恢复意图」。以 CLI 官方流式事件中报告的 `session_id`（或等价会话身份字段）等于绑定 `nativeSessionId` 才确认 `resumed`；超时或事件缺失 → `unknown`，不得按 argv 假定成功、不得推进覆盖。

## 8. 切换事务（Switch）与空闲判定

### 8.1 允许条件

| 条件                                                          | 判定                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------ |
| 无进行中回合（`running` / `queued`）                          | `SendTab` L87–89 思路                                  |
| 无内核排队（`queue` 记录，非视图 `pendingSends`）             | 迁移后排队在内核                                       |
| 无未决审批                                                    | `pendingPerms` 为空                                    |
| 无活跃后台工具 / 子代理                                       | 有完整跟踪且为就地空闲可过；**跟踪不全 / 未知 → 阻止** |
| 无非终态 `SwitchTxn`；无 `uncertain` attempt / `unknown` 绑定 | §8.2 / §6（**B 起即阻塞**，不因 C 增加 resume 而放宽） |
| 空闲保留的 warm 进程                                          | **不是**忙，不阻止切换（切换时按需 teardown）          |

### 8.2 状态机与「下一发送消费」不死锁（评审项 5）

```text
prepared ──torn_down──> bound ──committed_active──> committed ──(下一发送消费)──> drained
    └──────────── rollback ────────────┘
```

- **`committed_active`**：目标绑定就绪（旧进程已拆、新绑定已解析）即**提交激活**，写入 durable pending 计划；**切换本身不执行交接、不发任何用户任务**。
- **pending 计划可在下一发送时重算**：真实恢复结果出来后才定策略——resume 失败 → full；new / fallback → full；**官方确认之前**不记录、不声称 `resumed`。
- **能力未知不探测**：驱动没有**已证明的官方安全握手**时，不在切换或预发送阶段发起 resume 探测（不臆造 CLI 行为），直接按 full；resume 仅在驱动被证明支持安全恢复后启用。
- **下一发送**：允许在 `committed_active` 状态下发送（`SwitchTxn` 箭头 → `drained`，作为该发送的 attempt 自己的 txn 记录），发送时先消费 pending handoff：resumed → delta，否则 full。
- **死锁修复**：旧版「send 拒绝非终态 txn + 切换只等下一发送」的环被断开——切换在「就绪」处就是终态可发送状态（`committed_active`），消费发生在下一发送内部（下一发送有独立的 attempt txn，允许并存）。
- `recover`：启动读 txn，各阶段按 §9 的恢复规则推进或回滚；`committed_active` 而用户未发送 → 保持 pending（durable），重启后仍消费一次。

### 8.3 回滚与不确定性

- `rollback`：目标绑定指针退回 `fromBinding`（旧进程不塞回），pending handoff 丢弃；下次在旧 CLI 上发送按旧绑定恢复。
- `uncertain` attempt 或 `unknown` 绑定时，切换**拒绝**，先让用户处理不确定状态。
- 切换**不改动工作区文件**。

## 9. 崩溃恢复与迟到事件隔离

### 9.1 各阶段 failpoint（B2 落地时逐一注入测试）

| 写入点                                   | 崩溃后               | 恢复规则                                     |
| ---------------------------------------- | -------------------- | -------------------------------------------- |
| switch `prepared` 写后                   | 未拆进程             | 视为未开始，rollback                         |
| `torn_down` 写后                         | 旧进程可能已拆       | 幂等确认，不重复拆；进入 `bound` 计算        |
| `bound` 写后                             | 计划未提交           | 重算 plan                                    |
| `committed_active` 写后                  | pending 未消费       | 保持 durable，下一发送消费                   |
| attempt `planned` 后                     | 未写 CLI             | 标记可安全重试；用户决定                     |
| attempt `dispatching` 后 / `accepted` 前 | **可能已提交给 CLI** | `uncertain`，不自动重放，等待用户            |
| attempt `accepted` 后 / commit 前        | 文本可能部分丢失     | `uncertain`；不推进覆盖；用户决定            |
| commit 记录尾批无 commit 标记            | 不完整               | 丢弃尾批，按 checksum 校验通过的最后一条提交 |
| 镜像写后 / 权威提交后                    | 显示滞后             | 游标重放                                     |

### 9.2 不确定副作用

任何「可能已写入 CLI」的阶段都进入 `uncertain`，**没有自动重放**；只有用户显式确认「重试」才用同一逻辑 user 条目（`attempt+1`）再发，或选「放弃」（append 一条 `system` 说明，保持条目不重复）。

### 9.3 迟到事件隔离（裁决单元）

每个 CLI 事件附带/推导 `(conversationId, bindingId, generation, turnId, attempt)`。运行时丢弃任何字段不匹配当前活跃状态的事件；**取消会递增 `cancelEpoch`**，即使同一绑定，取消后迟到的 `startAutoTurn`（研究稿 2.7 提到的 `onClaudeLine` 在 `turn == nil` 时自动起轮）也必须被拒绝，不得开启未被用户触发的回合。该防护从 B3 接入编排器时即生效，属于 B 的安全范围。

## 10. 迁移（评审项 7）

### 10.1 原则

- **显式归属 / 映射，不按条数比较、不按 append 拼接**。CLI 标签的侧栏镜像通常 `0` 消息（F2），运行时须直接读**权威 harness 文件** `tabs/<tabId>.json`。
- 只迁移**与 convstore 会话有明确关联**的会话 / 标签；**不**自动迁移无关普通 Agent 标签（它们继续保持标签语义）。
- 原 `conversationId`、侧栏项 id、标题、`projectId`、时间戳**保持不变**。
- 已有消息 ID 冲突 / 缺失时，生成**确定性冲突映射**（`legacyMap`），**绝不覆盖**任何旧消息。
- 未被裁剪前已丢失的标签条目**不可恢复**（F2 的 `maxTabMessages`）；不声称可恢复。迁移只处理现存文件，`legacy-archive` 保留原始字节（含当前 reader 会跳过的坏行 / 超长行）。

### 10.2 步骤（迁移状态：`planned → staged → committed`；尚未实施）

```text
1. [冻结] 仅冻结明确托管的目标会话写入口（含其关联标签）；所有 ingress 已适配后才允许执行。无关 Agent 标签不冻结。
2. [规划] 对每个会话：
   owner = 显式映射表（development 内已知的 tabId ↔ conversationId；来自 ChatSession.tabId）
   sources = [ convstore messages/<id>.jsonl 原始字节, tabs/<tab>.json 原始字节（若存在） ]
3. [staged] 在 convstore 管理的隔离 staging 提交单元中构造升级数据：
   - convstore 消息：id 若缺 → 确定性生成 "legacy_" + sha256hex(conversationId + i)[:16]；
     重复 id → 第二个及以后改写 "legacy_" + sha256hex(id + order)[:16]，写入 legacyMap{old,new,source,order}
   - 标签消息：仅在「convstore 中没有同 id」时追加；来源标记 origin.cli / nativeSession 来自标签 cliSessionId
   - 冲突 / 无法对齐的 payload：原样写入 <conversationId>/legacy-archive.jsonl（含行号、来源文件、校验和）
   - 所有原始字节先备份到 conversations/backup/<conversationId>/（不自动清理）
4. [commit] 每会话校验通过后，正文+迁移/所有权状态在同一原子提交点生效；不存在先 committed 再 header 的窗口
5. [投影重建] 由同一 convstore 权威生成视图 DTO、索引与预览；旧 messages/<id>.jsonl 不再作为托管会话写目标
6. 提交前失败 → 保持该会话 v1；提交后失败 → 重启按已提交 v2 恢复，绝不覆回旧备份。其他会话分别记录状态。
```

- **冲突先于去重**：同 `id` 且规范化 payload 相同 → 只展示一条。同 `id` 但内容不同：**来源所有权明确**时，权威只取所有者的一条，另一条整体进 `legacy-archive`；**所有权不明**时，两条都不进权威，全部进 `legacy-archive`，并在迁移报告里给出可见警告（不静默丢数据）。任何情况下都不得按「缺 id 则追加」补入正文。
- **备份字节级**：备份是**原始字节**，含 images / tools / trace / 未知字段及其行尾与编码（与可安全省略的共享正文投影分开保存）。
- **幂等 / 一次导入**：按稳定来源标识 `(sourceKind, sourcePath, sourceIndexOrId)` 去重；重复运行只补缺；`committed` 已存在则跳过。
- **`migrated-unverified` 绑定**：若旧标签有 `cliSessionId`，建立 `NativeBinding{status:"unverified", coverage:{}}`——**覆盖率未知按保守 full**；下次在该 CLI 发送按 §7.2 能力门控：驱动具备已证明无提示安全握手时才探测，否则保留旧绑定并直接 new + full；探测无回执 → `unknown`，不静默重试、等用户决定（不保证「永远不提问」）。
- **孤儿标签**（标签存在、convstore 会话不存在）：不自动建会话；记录到迁移报告；保留原文件。
- **`uncertain` vs `unverified`**：迁移来的绑定只能 `unverified`（从未执行过本运行时发送），不得标 `uncertain`。

### 10.3 回滚与禁用（不得宣称可回滚「全部」）

- 迁移提交后**不解删**任何原始文件；备份 raw bytes 含坏行 / 超长行（`readLines` L451–500 当前会跳过的行）。
- **禁用运行时**：不恢复旧备份、不丢弃新产生的会话历史；保留 convstore 中最新权威和只读投影；通过同一读服务展示，不退回只含旧历史的 v1 文件。
- **真回滚**（仅限「迁移后尚未产生新数据」时提供）用 fresh 会话核对；一旦有新数据，仅做备份保留，不声称可回滚。

### 10.4 不迁移的东西

标签的工具 trace、推理、审批、图片不进入权威正文（保留原始文件）；标签消息上限截掉的部分不搬运。

## 11. 供应商缺失入口、登录三态、权限保守映射

### 11.1 选择是显式的

- `conversationRuntime.providers` 返回每个 CLI：`installed`（yes/no/unknown，来源 `bins` 现查 F7）、`version`、`auth`（`signed_in` / `signed_out` / `unknown`）、`localLogin`（yes/no/unknown）。
- **`--version` 成功只证明安装与版本，不证明已登录**；`auth` 只能由官方、无副作用的探测得到（如 CLI 提供只读状态命令），否则 `unknown`。
- **不隐藏自动运行**：无供应商时 UI 呈现「本机 CLI（Claude Code / Codex）」选项与「安装并登录后可用」引导；用户**显式选择**后才绑定运行。API 已配置时同样可选本机 CLI（不强制）。
- 登录由用户在 CLI 自己的界面完成；Nomi 不抽取凭据、不刷新 token、不读凭据文件。

### 11.2 未知登录

允许选中；首次发送如有官方 `auth_required` 错误，就原样转译并提示「在 Claude Code / Codex 中登录后重试」；不做凭据检查。

### 11.3 权限（B 起即保守，不推迟）

- 映射表按驱动提供；**不支持的档位 → 选一个支持的、保守的交互式档并显式确认，或拒绝该操作**；**绝不**默认「安全」或自动允许，**绝不**把不支持映射成 bypass / auto-approve。
- `bypass` 只能经显式二次确认（参照 `harness.tabSetPermission` 的 `expect` 语义，`harnessClient.ts` L658–659）。
- B 阶段内部预览必须带：保守权限 / 审批 / generation 隔离 / uncertain 不自动 / 未跟踪后台即阻止切换；**未达到这些安全门槛前不开放生产，也不宣称可用**。B 不实现完整的 D 阶段 UX（三控件、能力面板），但安全底线不能在 B 被推迟。

### 11.4 能力降级

`capabilities` 逐项声明：`images`（native/path/none）、`resume`、`fork`、`inPlaceModel`、`mcp`（实际注入项）、`skills`、`memory: none`、`knowledge: none`、`approval`、`sandbox`、`degraded[]`。Nomi 人设 / 记忆 / 知识库不注入 CLI；computer MCP 只在使用者的 CLI 侧配置中存在时可用。
