# 子任务对话与主对话对齐

状态：第一阶段已在 `feat/subagent-chat-parity` 落地。下面是建议的交互，以及还没做的部分。

## 建议

子任务不要再做一套缩小的侧栏会话。Nomi 委派出去的编程助手（Claude Code、Codex、ACP，以及任务页里同一类标签）在内核里本来就是 harness 标签，和用户自己开的编程助手标签是同一种会话。点「查看」应当把它变成当前标签，主对话列直接复用编程助手会话那条链路：`CliConversation`（里面是统一的 `ConversationView`）和 `MessageInput`，加上已经挂在主列上的提问卡、待发列表、停止、权限和模型。

侧栏不再被另一套会话占住。来源对话留在原来的标签上（通常是 Nomi 主对话），主列顶部一条返回条负责回去。父对话里的子任务卡片继续显示进度和结果。

不建议把子任务嵌进父消息列表里当一条线程。滚动、输入焦点、提问卡和工具展开会和父对话抢同一条时间线，外部 CLI 的转录也不是 Nomi 消息 id。也不建议只把缩小面板的输入框换成 `MessageInput` 却不切换当前标签：模型、权限、斜杠命令、提问卡和待发队列都认「当前标签」，侧栏里再挂一份会又变成一套特例。

## 现状，以及为什么会分叉

委派（`delegate_to_cli`，后台任务也一样）在 Go 里创建一个 harness 标签，`delegation.by = nomi`。消息、实时事件、权限队列、插话（`harness.tabSteer`）、发送（`harness.tabSend`，用户发起）和停止（`harness.tabCancel`）跟用户自己的编程助手标签是同一套。空闲时用户接着说不算接手；只有委派还在跑时用户发消息才标 `takenOver`。后续轮次用 `delegate.completed` 且 `followUp: true` 回到来源对话。

视图却把它排除在主对话之外：

- `useCliTabSync` 不把这类标签镜像进侧栏，避免委派会话出现在编程助手历史里。
- 点卡片或会话详情里的「查看」打开 `SubagentPane`，占对话旁边那一栏（原来的变更 / 文件预览让位）。
- 那一栏自己拉 `tabMessages`，直接渲染 `ConversationView`，底下是一个两行的 `Textarea`，外加模型按钮和「发送」。待发消息走另一份 `subagentQueue`，不走主列的 `HarnessTabsContext` 队列。

主列在当前标签不是 `main` 时，已经是完整的编程助手会话：`ChatBody` → `CliConversation`，输入栏是 `MessageInput`，上面有提问卡、待发列表、权限模式、模型 / 思考深度、附件、斜杠命令、语音、上下文环。侧栏那一栏打不到这条链路，是因为它没有把标签激活成当前标签，只能平行再做一份更少的 UI。缩小面板看起来「不自然」，原因是会话模型已经统一，呈现层又拆开了。

Nomi 自己的子代理不是这条路径。对话里的 `Task` / `spawn_agent` 是一轮里的工具时间线，没有独立的 harness 标签。`delegate_to_nomi` 是后台 Nomi 任务，出现在任务里，不是这个面板。

## 主对话有、缩小面板没有

「主对话」同时包括 Nomi 对话和用户自己开的编程助手标签。缩小面板是改之前的侧栏。第一阶段是本分支：委派标签激活后走编程助手主列。

## 目标交互

进入：子任务卡片、会话详情里的 Agents，仍然是入口。点「查看」记住当前 harness 标签（一般是 `main`，也就是正在看的 Nomi 对话），再 `activate` 委派标签。

查看：主列就是这个标签的会话。标题、工作目录、模型、权限、提问和待发都跟着它。顶部返回条显示助手名字、运行 / 等待确认 / 空闲、目标和一句说明（做完会回到主对话）。侧栏高亮留在来源会话上，因为委派标签本来就不进侧栏。

离开：返回条切回打开之前的标签。输入栏以外按 Esc 同样返回（输入栏里的 Esc 仍交给斜杠菜单、补全，或「停下并发送待发」）。从侧栏或快捷键切走时，只收起返回条，不再把当前标签拽回来。标签被关掉时回到来源标签。

父对话里的卡片不变：进度、停止这个任务、完成汇报仍在卡片上。跟子任务里再做的轮次，仍以 follow-up 写回来源对话。

## 数据与会话

第一阶段不改 Go 的会话模型。一次委派已经是一等的 harness 标签：

- 转录在标签的消息里，视图用现成的 `fromHarnessMessage`。
- 实时进度、权限、沙箱、后台子代理走现成的 live 事件。
- 发送、插话、排队、停止、编辑重发走 `HarnessTabsContext`，和用户自己的标签相同。`subagentQueue` 不再接到界面上（模块和单测还留着，确认标签队列覆盖同一组竞态后再删）。
- 草稿按 `tab:<id>` 存在主输入栏的草稿桶里。
- 来源对话的消息仍在 Nomi 会话里。查看子任务时不切换 ConversationStore 的当前会话，返回主标签时 `useRestoreNomiOnMain` 也不会把会话指丢。

以后如果要把 Nomi 自己的子代理也做成这种会话，需要内核给它一个稳定的会话 id 和与 harness 同形的消息流。现在没有，所以不能假装它已经是一个标签。

## 外部 CLI 和 Nomi 自己的子代理

沿用编程助手标签已经做好的降级，不在子任务上再写一套：

- 不能插话的 CLI（Gemini、dsh、部分外部 CLI / exec 退路）：`tabSteer` 失败或能力位表明不支持时，消息改排队，这一轮结束后再发。
- 不能发图的 CLI，或当前模型不能看图：输入栏留下图片并说明，不悄悄丢掉。
- 权限档：清单里没有的档降到更安全的一档，和普通标签相同。
- 提问：Claude Code、Codex app-server、ACP 表单走主列的提问卡。没有来回通道的（Codex exec 退路）仍然问不了。
- 委派还在跑时用户发送：内核仍视为接手（`takenOver`）。空闲时接着说，结果照样 follow-up 回父对话。

不进这个视图、界面上保持原样的：

- CLI 内部子代理（`Task`、`spawn_agent`、不暴露步骤的 `subagent`）：仍是时间线里的一块。没有单独会话可以打开。
- `delegate_to_nomi`：仍是任务，不进这条返回条。
- 没装编程助手时主列不会停在 CLI 标签上（现有逻辑会切回主对话）。委派本身也起不来。

## 分阶段

1. **本分支。** 点「查看」激活委派标签，主列复用编程助手会话和输入栏；返回条负责回来源标签；侧栏高亮留在来源会话；会话详情不再因为「子任务栏」收起或改成浮层。内核的 follow-up、接手规则、不进侧栏都不改。
2. **导航补全。** 返回条写上来源会话的名字；父卡片上能看出「正在主列里看」；评估要不要在侧栏给委派标签一个从属入口（现在刻意不进历史）。删掉不再使用的 `subagentQueue`。统一「停止」：卡片对持续任务走 `tasks.cancel`，主列的停止走 `tabCancel`，两处含义不同，需要对齐产品口径。
3. **Nomi 自己的子代理。** 只有内核给出一等会话之后，才用同一套主列打开。在那之前继续用时间线，避免做第三套 UI。

## 开放问题

1. 主列替换来源对话，是否符合预期？另一条路是侧栏仍开着，但嵌入同一套组件。那样父对话还看得见，但模型、提问卡和队列都认当前标签，侧栏里会再做一份特例，窄列也放不下完整输入栏。
2. 委派标签要不要出现在侧栏（作为来源会话的子项）？现在不出现，是为了不把委派会话混进编程助手历史。
3. 跟子任务接着说的结果，是否仍要写回父对话？第一阶段保持写回。如果主列就是「正在和它说话」，有人会觉得父对话里再贴一份是重复的。
4. 运行中发送算接手（打断 Nomi 这轮、之后 Nomi 不再往这个标签派活）要不要保留？这是现有内核规则，第一阶段没改。
5. 持续任务的「停止」以取消任务为准，还是以打断当前轮次为准？卡片和主列今天不是同一件事。
6. Nomi 进程内的子代理（不是外部 CLI）要不要做成可打开的会话？需要单独的会话模型，建议单独立项。
