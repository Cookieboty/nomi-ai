# 2.5.0 B2c：接通官方 Claude CLI 的受限主对话运行时

状态：**生产 factory 已接入既有主对话 typed IPC；仅显式 opt-in 的实验能力，不是 2.5.0 完工或默认开放。** 全部进程验收使用临时目录内的假可执行文件，没有运行用户安装的 CLI、读取凭据、调用模型或操作真实 userData。

## 1. 实际生产路径

`main.go → wireManagedClaude → mainchat.RegisterOwned("claude") → conversations.runtimeAdopt/Select/Send → leased Session → claudert.Runtime → claude.OfficialLaunch / claude.NewParser / drivers.StreamJsonDriver / nodeproc`。

- factory 只做 `LookPath`、普通路径/可执行文件 metadata 校验，不执行 `--version` 或 `auth status`，不读取账户凭据。未找到 executable 不广告 Claude backend；**存在 executable 不等于已登录或版本兼容**。
- 当前须会话选择了一个既有 project，以 primary folder 为 cwd。没有 project 时明确拒绝 adopt，不悄悄使用 home；通用 providerless 新会话工作目录/首用 UI 尚待实现。
- 默认官方 config source 取 `CLAUDE_CONFIG_DIR` 或 home 下 `.claude` 的路径，交给 CLI 自行使用本机登录。沿用官方 plugin 的 strip/env，不复制 OAuth 或解析 CLI 转录。
- executable 身份/大小/mtime、物理 cwd/目录身份、config source、model/permission profile 进入 compatibility key。替换 cwd（含 symlink retarget）、可执行文件或账户来源不会覆盖原 binding，也不会偷偷复用旧 worker。
- 不调用 gateway/provider prepare，不进入 harness Agent 标签，不再包一层 Nomi agent loop。既有 product conversation ID 和 convstore S1 单写者不变；视图不重复保存 CLI 消息。
- `RegisterOwned` 在 release/delete/shutdown 时清理该会话全部 compatibility variant 的 worker，包括当前选中 API 而暂存的 warm Claude。释放回调在 registry/session lock 外执行；释放期间不能重开 actor，shutdown 等待进行中的释放。

## 2. 官方协议及保守能力边界

复用仓库现有的 2.1.318 stream-json 合同 profile，不声称已对用户安装版本做兼容性实测。官方命令参数为 `-p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --replay-user-messages`，通过 stdin 提交 **一次且仅一次 `Plan.Payload`**。不是把历史另发成原生工具调用，也不重复追加当前请求。

当前限制：

- `--safe-mode --restricted --disable-slash-commands --setting-sources '' --settings '{"disableAllHooks":true}'`；`--tools Read,Glob,Grep`，严格空 MCP 配置并禁止 `mcp__*`。不使用自动允许工具、`acceptEdits`、`bypassPermissions`。managed policy 仍可能生效；观察到 hook/task/subagent/不支持的 tool 或有效权限模式变化则 fail closed。
- **不能使用 `--bare`**：官方文档明确 bare 不使用订阅 OAuth/keychain 登录，会直接破坏本需求的本机登录复用。
- product `ask` 映射 plugin 的 `manual` → native `default`。native default 下部分只读工具本来就可无提示运行，不能宣称“每次 Read 都必须审批”。收到的受支持权限请求只有显式 allow/deny 才应答，allow 只返还原始 native input；未知 tool/伪造或旧 generation 的 approval 不可自动批准。完整权限说明/审批 UI 尚待交付。
- native loop 自己执行只读工具；本轮不提供 shell、写文件、subagent、background task、native MCP 或 skills。Nomi computer/persona/memory/knowledge/attachments 均**没有桥接**，capabilities 的 degraded 明示这些限制。历史附件仍由 convstore 保留、planner 记录遗漏；当前附件沿用托管入口显式不支持门禁。
- 文本缓冲到有效成功 result 后才进入 product draft/reply，不传 reasoning、tool state；也保留只有 result.text 没有 assistant frame 的合法结果。尚非逐 token UI 流。
- stdout 在 shared driver 的 splitter 前约束单行/未结束行至 2 MiB，拒绝无效 UTF-8/JSON/未知协议和 native identity 改变；正文亦有界。共享 driver 的“exit 也 resolve / 部分文本后非零退出”不是成功证据。

## 3. 恢复、交付和取消的真实语义

| 情况                                                                                                                                            | 实际结果 / 规划                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 首次 native                                                                                                                                     | 官方 `--session-id <UUID>`，initialize 成功只表示 transport 已准备；`RecoveryNew` → bounded full         |
| 同一已完成 worker、同一兼容 binding                                                                                                             | `RecoveryResumed` → delta；切到 API 再切回亦保留这个 worker/SID                                          |
| 冷 `--resume <SID>`，只拿到 initialize 或 init.session_id                                                                                       | **不是 resumed 证据**；停止本次 worker，`RecoveryUnknown`，绝不提交 user frame，不发旧 delta，不自动重放 |
| 冷 resume 在任何 user frame 前以 exit 1 明确退出且唯一 stderr 为官方 `No conversation found with session ID: <exact-SID>`，并已证明该进程组停止 | 新 UUID / 新进程，`RecoveryFallback` → full；旧 binding/coverage 原样保留                                |
| 其他初始化错误                                                                                                                                  | 无用户输入且证明已停止才 `RecoveryError`；否则 unknown                                                   |
| 提交后错误、正常/非零退出但没有有效 result、未解决 approval/tool、身份冲突                                                                      | uncertain；不生成成功 assistant、不自动重放                                                              |

新 native 的 init/session SID 必须匹配预定 UUID；warm native 同样不得改 SID。delivery ACK 只来自匹配 native SID 且 UUID/完整文本一致的 replay-user frame，或已验证的 successful native result；**写入 stdin、initialize 成功本身都不是 ACK**。复用 B1 精确 plan receipt/revision 规则，旧 generation 的输出不能改历史、coverage 或 approval。

完成前原子交接 worker 的 warm 状态，并解除该 turn 的 context watcher，避免 Session 在完成时取消 attempt context 连带杀掉 idle worker。owner release 仍会结束它。完成后观察到新的 native 工作，标记该 generation 的 activity unknown，不能继续当 idle 切换；已切换/取消 generation 的此类通知会被围栏拒绝。

取消不是把 native interrupt ACK 当“已停止”：杀死独立进程组，等待 root close 且进程组消失才 `CancelStopped`，否则 `CancelUnknown`。已知退出的 PID 不再发送 group signal，避免长期缓存 PID 复用风险；已确认的 stop evidence 可重用。Windows 路径不假装支持 process-tree stop。

**重要未完成项**：官方冷 resume 没有已证明的 pre-prompt 恢复 ACK。已有 native session 在正常 release/restart 后通常进入上述 unknown 门禁，目前没有生产“重置旧 native binding 并新建 full”交互/事务；不能称为跨重启无缝续接。完整 switch prepare/recover/handoff/commit、冷恢复证据或显式新会话决策，应在后续有界切口实现，不能凭 fake 多加一个官方没有的握手字段。

## 4. 验收证据与还未接通的部分

`conversation_claude_test.go` 使用真实 typed IPC + 真实 OS 子进程 + 官方 driver/parser，factory 指向临时 fake Python executable：

- 无 gateway/provider 实例的真实 adopt/send；同 sidebar ID/history 的 Claude → API fake → Claude；只启动一个 native worker，首次 full、切回 delta，当前请求恰好一次。
- 检查官方 argv、cwd/config source、移除 fake API key、没有 bare 或自动允许参数；root wiring 测试证明发现/adopt 不执行 CLI 或登录探测，无 project/无安装不静默迁移。
- startup error、clean/nonzero exit、partial text 后非零退出、malformed/oversized event、SID mismatch、native error、unsupported tool 都不能伪造成功。
- 显式 allow/deny 原生审批、原始 input 完整、伪造 ID 拒绝；cancel 后 buffered late text 不落库；无 echo 不提前 ACK；result-only 文本不丢失。
- 冷 initialize 不能假 resumed；已知 missing resume 才新建 full 并保留两个独立 binding；旧 coverage 不过滤新的 full。
- late background 不能假 idle；owner release/shutdown 与并发重开不死锁；compatibility 改变不覆盖旧 native 身份。
- 完整 conversationruntime、convstore、mainchat、shellhandlers、API router、Claude plugin/driver、contracts/archguard 与重复 race 回归，不跳过既有 B1/B2a/B2b assertions。

现有 managed API 仍是**显式 opt-in 的实验性纯文本**，没有 tools/approval parity；未托管的旧 API tool 路由完全不替换。本轮不改 frontend/IPC schema，已有 typed runtime ingress 和托管发送分支被复用；没有声称普通 UI 已提供 providerless backend/account/model 选择或可知情审批。

Windows 的 managed persistence gate 仍在任何 adopt/migration 前，旧 API 可用/可读；**Windows 功能没有完成**，也未在 macOS/Windows 或真实官方 CLI 上验收。

下一个建议切口：先补受限 Claude 的显式 cold-unknown → 用户决定新 native/full 的 durable recovery/switch 事务，并以同一入口贯通 providerless 首用/选择/错误提示；再接官方 Codex factory，补 API tool parity、native 权限 UI、Windows 原生耐久写入与平台 CI。不要再建平行 fake-only registry/store。

## 本轮实际执行结果

- Go（含应用 root 的 `-tags gtk3`）：11 packages，210 个顶层测试 + 137 个子测试通过；不跳过既有 runtime/convstore/API 断言。
- 受影响内核/IPC/Claude plugin/driver/contracts/archguard：10 packages 的 race + shuffle 重复 3 次，576 个顶层 + 378 个子测试通过；root 的 18 个顶层/11 个子测试只在普通 Go 测试中执行，未声称 root race。
- Linux 实际应用 `go build -p 1 -tags gtk3` 链接成功，产物仅保存在 box 验收路径，未运行。完整 `go vet`（含 root）、contract 173 tests、root 脚本 130 tests、托管前端 3 files / 11 tests、普通 typecheck 20 tasks 以及 frontend/i18n/character/changelog guards 均通过。未修改 frontend/IPC schema，本轮没有重新跑完整 ai-chat 2723 tests 或重建前端 assets。
- 新增 bad-UTF8 断言实际暴露了 `nodeproc` 逐 chunk 字符串替换行为：原 adapter 无法识别非法原始字节，也可能损坏跨 chunk 的合法 emoji。仅在本 adapter 使用 bounded raw-byte 增量 UTF-8 解码修复，保留全局 nodeproc 的旧语义；原失败断言未放宽，新增真实子进程分块中文/emoji 回归通过。malformed 后同一 chunk 内伪 replay/result 也不能再 ACK。
- 最初并发执行 vet/前端曾耗尽 root inode，两个命令报 ENOSPC，均已原要求重跑通过；未删除共享缓存、其他 worktree 或素材。`/dev` 创建私人目录的普通尝试因权限不足失败，没有提权；最终只把 vet 的**不需执行的中间数据**放到已允许写入的私人 `/dev/shm` 目录，noexec 保持不变，Go 工具/缓存和所有 fake executable 仍在常规可执行文件系统。完成后恢复环境并仅移除空私人目录。
