# 模型质量（设计稿）

> 状态：已实现（v2.0.0）。实现偏差见 §10。起草 2026-10-24；§8 的待确认项已按建议定下；官方账号补充 CLI 层口径（§1、§4.4）。
> 背景：「用量与费用」里的「最近请求」只在内存里保留 200 条，只能看单条，看不出某个供应商、模型、Key 的整体表现，也没法对比。
> 本稿把它拿出来，新增独立的「模型质量」菜单：持续记录每次请求的质量数据，按供应商 / 模型 / Key 等维度汇总和对比。

## 1. 目标与范围

**要回答的问题**

- 这个供应商 / 模型 / Key 稳不稳：成功率、失败率、失败原因分布、断流率。
- 快不快：首字延迟（TTFT）、每 token 间隔（TPOT）、端到端耗时（E2E）、输出速度（tok/s），看分位数而不只是平均。
- 省不省：缓存命中率、token 与费用。
- 同一个模型在不同供应商之间、同一供应商的不同 Key 之间、不同时间段之间，谁更好。

**统计范围与测量口径**

| 流量                                | 网关层（HTTP 请求，最精确）           | CLI 层（Nomi 读 CLI 输出流） |
| ----------------------------------- | ------------------------------------- | ---------------------------- |
| Nomi 对话                           | 有                                    | —                            |
| 编程助手 · 第三方供应商             | 有（带标签令牌，可关联标签）          | 有                           |
| 编程助手 · 官方账号（在 Nomi 里用） | 无（直连官方，Nomi 不在 HTTP 链路上） | 有                           |
| 终端里直接用的 CLI                  | 无                                    | 无（不在 Nomi 里运行）       |

- **网关层**：每个 HTTP 请求一条，有 TTFB、Key、尝试与回退、协议细节。
- **CLI 层**：Nomi 自己拉起 CLI 并读它的输出流，所以官方账号也能测：每一轮（Claude 可细到每次模型调用）的开始、第一个输出、最后一个输出、结束、结果（成功 / 失败 / 停止 / 进程退出）、CLI 报告的 token 与缓存、API 重试次数。没有 HTTP 首字节、没有 Key；时间含 CLI 自身开销（启动、工具执行不计入模型调用时，但「一轮」会包含工具时间，所以 CLI 层优先按模型调用计，拿不到时按轮）。
- 两种口径不混算：界面上分开显示或明确标注。第三方标签两层都有，因此「同一个 CLI，官方账号 vs 第三方供应商」可以在 CLI 层同口径对比。

**不做**：不记录对话内容（只有元数据）；不上传；不替用户自动切换供应商（只给数据，路由策略另议）。

## 2. 指标定义

所有时间都在网关上测量，起点 `t0` = 网关收到客户端请求。

### 2.1 计数与比率

| 指标   | 定义                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| 请求数 | 客户端发来的请求数（一个请求可能尝试多个候选）                                |
| 尝试数 | 实际发往上游的次数（换候选、重试各算一次）                                    |
| 成功   | 流式：收到上游结束标记并完整转发给客户端；非流式：2xx 且正文完整              |
| 失败   | 见 §2.3 的分类；**不含**用户取消                                              |
| 取消   | 客户端在结束前断开（用户停止、关标签、CLI 自己中止）                          |
| 成功率 | 成功 ÷（请求数 − 取消）。取消不算失败，也不进分母；界面可切换「取消计入分母」 |
| 失败率 | 失败 ÷（请求数 − 取消）                                                       |
| 取消率 | 取消 ÷ 请求数，拆成「首字前取消」与「输出中取消」                             |
| 断流率 | 已开始输出（过了提交点）的流里，没有正常结束的比例                            |
| 回退率 | 第一个候选失败、由后续候选完成的请求比例                                      |

**按哪一级计数**（重要）：「请求」视角（客户端 / 模型）按请求计；「供应商 / Key」视角按**尝试**计。例：Key A 失败后回退到 Key B 成功，对客户端是 1 次成功，对 Key A 是 1 次失败、Key B 1 次成功。否则失败的 Key 会被后面的成功掩盖。

### 2.2 延迟与速度

| 指标     | 定义                                                   | 备注                                                                                                                                                              |
| -------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TTFB     | `t0` → 上游响应头                                      | 网络与排队                                                                                                                                                        |
| TTFT     | `t0` → 第一个内容事件（正文、推理、工具参数任一）      | 即提交点；含回退耗时。另记「首个正文 token」时间，推理模型可分开看                                                                                                |
| E2E      | `t0` → 最后一个字节写给客户端                          |                                                                                                                                                                   |
| 生成时长 | 第一个内容事件 → 最后一个内容事件                      |                                                                                                                                                                   |
| TPOT     | 生成时长 ÷（输出 token − 1）                           | 输出 ≥ 2 且为流式才有                                                                                                                                             |
| 输出速度 | 输出 token ÷ 生成时长（tok/s）                         | 另给「整体速度」= 输出 token ÷ E2E                                                                                                                                |
| 突发度   | 生成时长 < 100 ms 且输出 ≥ 20 token 时记为「整段吐出」 | 上游表面流式、实际缓冲后一次给出（例：经 Amux 调 volcengine 的 deepseek-v4.1-flash，首字延迟 = 总耗时）。这类请求的 TPOT / tok/s 没有意义，单独计数并在对比中提示 |

每个延迟指标给 **p50 / p90 / p99 与平均值**，样本数不足（< 20）时只显示中位数并标注。

### 2.3 失败分类

| 类别            | 判定                                      | 归属                                 |
| --------------- | ----------------------------------------- | ------------------------------------ |
| 鉴权失败        | 上游 401 / 403                            | Key                                  |
| 限流            | 上游 429，或提交前收到限流错误事件        | Key                                  |
| 上游 5xx / 过载 | 5xx、529、提交前的过载错误事件            | 供应商                               |
| 首字超时        | 规定时间内没有响应头 / 没有第一个内容事件 | 供应商                               |
| 提交前出错      | 200 后、第一个内容事件前收到错误事件      | 供应商                               |
| 断流            | 提交后上游没发结束标记就断开              | 供应商                               |
| 空闲超时        | 提交后 N 秒没有任何输出                   | 供应商                               |
| 协议不合规      | 规范化层无法修复、只能报错的上游输出      | 供应商（附违规详情）                 |
| 复读中止        | 网关检测到复读并中止                      | 模型                                 |
| 请求被拒        | 400 / 404 / 上下文超长等请求本身的问题    | 请求（默认不计入供应商质量，可切换） |
| 网关自身        | 网关内部错误、没有可用候选                | Nomi（单独显示）                     |

### 2.4 缓存与用量

- **缓存命中率（按 token）** = 缓存读 ÷ 输入总量。输入总量按统一口径：OpenAI 系的输入已含缓存部分；Anthropic 系为「输入 + 缓存读 + 缓存写」。
- **缓存命中率（按请求）** = 有缓存读的请求 ÷ 请求数。
- 另记输入 / 输出 / 推理 token 与费用（复用现有定价）。

## 3. 维度与对比

**维度**（可任选一个作分组，其余作筛选）：

- 供应商、Key、模型（对外名 `供应商/模型`，以及上游真实模型名）
- 模型族（归一后的名字，如 `deepseek-v4.1-flash`，用于「同一模型跨供应商对比」）
- 客户端（Nomi / Claude Code / Codex / Grok / Gemini / dsh / 外部 CLI）
- 协议（入口协议 → 上游协议、透传 / 转换）
- 模型解析方式（显式 / 绑定 / 档位 / 辅助…），用于区分主对话与辅助请求
- 是否推理请求、是否流式
- 时间（小时 / 天）

**对比方式**

1. **分组表**：选一个维度，每行一项，列为 §2 的指标，可排序；每格带与上一周期相比的升降箭头。
2. **并排对比**：勾选 2～4 项（例：同一模型的 3 个供应商），按指标并排显示，并叠加趋势曲线。
3. **快捷对比**：「同一模型跨供应商」「同一供应商跨 Key」「本周 vs 上周」。
4. **钻取**：从任一格点进请求明细（已按该组合筛选），再进单条请求的追踪（诊断日志开着时）。

## 4. 数据采集

### 4.1 网关侧新增字段（`UsageEvent`）

现有：状态码、总耗时、首个内容时间（提交点）、尝试次数、用量、错误文本、标签、追踪 id。补充：

```ts
interface QualityTiming {
  headersMs?: number; // TTFB
  firstContentMs?: number; // TTFT（提交点，已有 firstByteMs 改名保留兼容）
  firstTextMs?: number; // 首个正文 token
  lastContentMs?: number; // 最后一个内容事件
  endMs: number; // E2E
}
type Outcome =
  | 'ok'
  | 'client-cancel'
  | 'http-error'
  | 'first-byte-timeout'
  | 'pre-commit-error'
  | 'stream-break'
  | 'idle-timeout'
  | 'protocol-violation'
  | 'repetition-stop'
  | 'request-rejected'
  | 'gateway-error';
interface AttemptRecord {
  // 每个候选一条，供 Key / 供应商视角按尝试计数
  provider: string;
  keyId: string;
  model: string;
  upstreamWire: Wire;
  status?: number;
  outcome: Outcome;
  ms: number;
  headersMs?: number;
  errorKind?: string;
}
```

- `outcome` 在网关的结束路径上直接判定（现在这些分支已存在：`res.on('close')`、首字超时、提交前错误、`passthroughFail`、空闲超时、复读中止），只是没有归类上报。
- 取消要区分「首字前」与「输出中」：看断开时是否已过提交点。
- `lastContentMs` 由协议桥在每个内容事件时更新时间戳，开销是一次 `Date.now()`。

### 4.2 主进程存储

- 新增 `QualityLedger`：每次请求一条记录（含 `attempts[]`），追加写入 `userData/usage/quality/YYYY-MM-DD.jsonl`（0600），与用量账本同目录、同受「用量统计」总开关控制。
- 保留：默认 30 天，可选 7 / 30 / 90 天；一键清空。
- 体积估算：每条约 400 字节，每天 5000 次请求约 2 MB，30 天约 60 MB 以内。
- 查询：按时间范围读取当天及历史文件，内存中聚合；分位数用排序或 t-digest。最近 7 天结果缓存，新记录增量更新。
- 「最近请求」改为从这里读最新记录，不再单独维护 200 条的内存列表（旧的 `requests.json` 迁移一次后删除）。

### 4.3 关联

- 带标签令牌的请求有 `tabId`，可从对话里的一轮跳到它的请求；也可反向从请求跳到标签。
- 每条消息上显示的模型（另一项功能）与这里的记录用 `tabId + 时间` 对应。

### 4.4 CLI 层采集

- 编排器在每一轮（及能拆出的每次模型调用）结束时生成一条 `layer: 'cli'` 的 `QualityRecord`：
  - 时间：发出 → 第一个内容事件（正文 / 推理 / 工具调用）→ 最后一个内容事件 → 结束；
  - 结果：正常结束 `ok`；用户停止 `client-cancel`（区分首字前 / 输出中）；CLI 报错 `cli-error`；进程中途退出 `cli-exit`；
  - token：CLI 上报的用量（含缓存读写）；重试：CLI 报告的 API 重试次数（如 Claude 的 `api_retry`）；
  - 模型：CLI 报告的模型，否则标签当时的模型；来源：官方账号（带 `accountId`）或第三方。
- Claude 的输出流按消息（`message.id`）给出每次模型调用的用量，可拆成「每次模型调用」一条；其它 CLI 按轮。

## 5. 界面

新增设置菜单「模型质量」（与「用量与费用」并列，放在「模型」组里），四个标签：

1. **总览**：时间范围（今天 / 7 天 / 30 天 / 自定义）+ 客户端筛选；顶部指标卡（请求数、成功率、p50 TTFT、p50 输出速度、缓存命中率、断流率）；失败原因分布；按供应商的简表。
2. **对比**：§3 的分组表、并排对比、快捷对比；指标列可选显示。
3. **趋势**：选指标与分组，按小时 / 天画折线，可叠加多项。
4. **请求明细**：原「最近请求」搬到这里，加上筛选（维度、结果、时间）、按列排序、每条的时间线（TTFB / TTFT / 生成 / 结束）、失败原因、追踪链接。

「用量与费用」里保留一个入口链接到「请求明细」。官方账号的编程助手在这里标「官方账号不经网关，无质量数据」。

视觉按现有规范：CSS Modules + `--cd-*` 令牌；表格与图表遵循 dataviz 规则（色板、深浅色、可访问性）；空数据、样本不足、只有官方账号三种空状态。

## 6. 隐私

只记录元数据（时间、状态、token、模型名、供应商与 Key 的 id）；Key 只显示名字或掩码；不记录正文、提示词、工具参数。与用量统计同一个总开关；可一键清空；全部只存本机。

## 8. 已确认（按建议）

1. 成功率默认把「取消」排除在分母外，可切换。
2. 「请求被拒」（400 / 上下文超长）默认不计入供应商失败率，可切换。
3. 默认保留 30 天（可选 7 / 30 / 90）。
4. 菜单放在「模型」组，紧挨「模型」页。
5. 支持导出 CSV（请求明细与对比表）。

## 9. 契约

记录、查询、结果与 IPC 的类型在 `packages/types/src/quality.ts`（`QualityRecord`、`QualityQuery`、`QualityResult`、`QUALITY_IPC`），网关采集、主进程存储聚合、界面三部分按它并行开发。

## 10. 实现偏差

- **CLI 层按轮记录，不拆成每次模型调用**（§4.4 原计划优先按调用拆）：编排器拿到的输出流里看不到 Claude 每次模型调用的发出时间（它发生在上一个工具结果之后），拆分不可靠。因此 CLI 层的一轮时间包含工具执行时间；CLI 自发的后台轮次（子代理结束后的跟进）不记。
- **CLI 层没有缓存写与推理 token**：CLI 上报的用量（`HarnessUsage`）里没有这两项。
- **网关修正备注**：契约补了 `notes`（网关对请求做的修正），请求明细里显示；原设计没列这一项，旧「最近请求」移除后需要它。
- **聚合在主进程里算**：30 天 × 每天 5000 次请求时，未命中缓存的分组查询约 0.5 秒；最近 7 天常驻内存、结果有缓存。数据量再大时把聚合挪到 worker 线程。
- **CSV**：请求明细一次最多导出 1000 条。
- **网关包不依赖 `@nomi-ai/types`**：结果类别、时间点、尝试记录在网关里按契约另写一份，electron 测试在编译期核对两份一致。
