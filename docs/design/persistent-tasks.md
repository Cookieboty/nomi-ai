## 1. 背景与目标

Nomi 现在做的每件事都挂在一次对话上：

- 委派给编程助手的子任务属于某一轮对话，应用重启后统一标为「中断」（`DelegateService` 启动时的处理）；
- 定时代理任务（每日简报）到点只能用对话模型生成一段文字；
- 提醒到点只发一条通知。

**目标：让「任务」脱离对话、单独存在。** 用户交代一件事，Nomi 把它记成一个有生命周期的任务：按约定的时机推进，
需要人的时候来找你，结束时给出交付和证据；应用重启后状态仍然可靠。

用户能说的话举例（GitHub 只是事件来源之一）：

| 说法                                                   | 触发     | 执行者   | 需要的授权            |
| ------------------------------------------------------ | -------- | -------- | --------------------- |
| 每天 9 点看一下 X 仓库的 CI，红了告诉我                | 定时     | Nomi     | 只读、联网            |
| 下载文件夹里出现新 PDF 时，总结一下放进知识库          | 文件夹   | Nomi     | 读该文件夹、写知识库  |
| 这个 RSS / 网页更新了就提醒我，附上变化                | 网页轮询 | Nomi     | 只读、联网            |
| 这个 issue 有新回复时，让 Codex 在隔离分支里试着修一下 | GitHub   | 编程助手 | 只读 + worktree 写入  |
| 每周五汇总这周所有编程助手会话做了什么                 | 定时     | Nomi     | 只读本机会话记录      |
| 刚才那个重构让 Claude Code 接着做完，做完叫我看 Diff   | 手动     | 编程助手 | worktree 写入、跑命令 |

一句话：**交代一次，Nomi 一直记着。**

### 不做的事（2.1.0）

- 不承诺应用退出、系统休眠或离线时继续执行（§10.4）；常驻服务、远端执行另行评审。
- 不做通用多代理编排（DAG、角色交接）；任务不能创建任务（§8.5）。
- 不自动合并、发布或做生产操作；这些永远要人逐次决定。
- 不开放本机监听端口接收 webhook（§6.4）。
- 不引入数据库；不嵌入 Super-agent / dsh 的任务引擎（#219 方案 B、C）。

## 2. 现状（代码事实，2.0.9）

| 现有机制     | 位置（Node / Go）                                                                    | 本质                                                            | 限制                             |
| ------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------- | -------------------------------- |
| 提醒         | `core/src/desktop/reminders/ReminderStore.ts` / `internal/core/desktop`              | 定时触发 → 系统通知                                             | 只能通知                         |
| 定时代理任务 | `core/src/schedule/SchedulerService.ts` / `internal/core/schedule`                   | 定时触发 → 对话模型生成文字 → 气泡 + 通知；错过 12 小时内补跑   | 不能用工具，没有授权、预算、状态 |
| 委派         | `core/src/cli/delegate/DelegateService.ts` / `internal/core/cli/delegate`            | 手动触发 → 编程助手；worktree 隔离、接管、最多 3 个并行         | 绑定对话；重启即中断             |
| 命令自动审核 | `core/src/desktop/commandReview.ts`、`PermissionBroker.ts` / `internal/core/desktop` | 风险分级 low/medium/high/critical；读过外部内容后中风险也要确认 | 只在前台，确认 = 弹卡片          |
| 用量         | `core/src/usage` / `internal/core/usage`；2.0.9 起按每次上游请求记账                 | 每次请求的 token 与费用                                         | 没有按任务归属                   |
| 通知与免打扰 | `DesktopService.notify`、`SchedulerService` 的免打扰时段                             | 系统通知、气泡                                                  | —                                |

结论：执行能力（Nomi 工具、编程助手、worktree、审批）、触发（定时）、投递（通知、气泡、免打扰）都已具备，缺的是
**一个持久的任务对象**把它们串起来。

## 3. 核心决定：一个任务模型，收编现有机制

不新增第四套系统。提醒、定时代理任务、委派子任务都是同一个 Task 模型的特例：

```
Task = 目标 + 触发器 + 执行者 + 授权 + 预算 + 若干次执行（Attempt）+ 待投递（Outbox）
```

| 现有机制     | 触发器 | 执行者   | 迁移后                                                           |
| ------------ | ------ | -------- | ---------------------------------------------------------------- |
| 提醒         | 定时   | `notify` | 一次性或重复任务，执行者只发通知                                 |
| 定时代理任务 | 定时   | `nomi`   | 授权默认只读；原来的「只生成文字」= 不给工具的 Nomi 执行         |
| 委派         | 手动   | `cli`    | 前台委派仍可即时等结果；「后台委派」就是一个任务，可以重启后继续 |

迁移规则见 §13。前台的同步委派（`background:false`）不变：它是对话里的一次工具调用，不产生任务。

## 4. 概念与数据模型

### 4.1 术语

| 术语                  | 含义                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------- |
| 任务（Task）          | 用户交代的一件事；有目标、触发器、执行者、授权、预算、状态。身份是 `taskId`，与对话无关 |
| 触发器（Trigger）     | 何时开始一次执行：手动、定时、事件                                                      |
| 事件源（Source）      | 产生事件的插件：文件夹、网页、GitHub、MCP、应用内部事件……（§6）                         |
| 执行者（Executor）    | 谁来做：`notify` / `nomi` / `cli`（§7）                                                 |
| 授权（Grant）         | 用户批准给这个任务的能力、范围、期限（§8）                                              |
| 执行（Attempt）       | 任务的一次运行；带代次号 `gen`。一个任务可以有多次执行                                  |
| 副作用日志（Journal） | 这次执行做过的有影响的动作，重启核对用（§10）                                           |
| 待投递（Outbox）      | 要发给用户的结果、请求；发送状态单独记录（§11）                                         |
| 收件箱（Inbox）       | 需要用户处理的任务（等你决定、待核对、待验收）                                          |

### 4.2 记录（草案）

```ts
interface Task {
  id: string; // task_<uuid>
  title: string; // 用户可读，Nomi 起草、用户可改
  goal: string; // 交给执行者的目标说明（用户原话 + Nomi 整理）
  origin: { conversationId?: string; createdBy: 'user' | 'nomi'; createdAt: number };
  trigger: Trigger;
  executor: ExecutorSpec;
  grantId: string; // 指向当前有效的授权
  budget: Budget;
  status: TaskStatus; // §5
  enabled: boolean; // 暂停整个任务（不影响已在跑的执行，见 §5.3）
  lastAttemptId?: string;
  nextRunAt?: number; // 定时触发器算出
  acceptance: 'auto' | 'user'; // 完成后要不要用户验收（§5.4）
  updatedAt: number;
  schemaVersion: 1;
}

type Trigger =
  | { kind: 'manual' }
  | { kind: 'schedule'; repeat: Repeat; at: string; tz?: string; catchUpMs?: number } // 复用 recurrence
  | { kind: 'event'; sourceId: string; filter: unknown; cooldownMs?: number; mode: 'observe' | 'act' }; // §6；mode 见 §6.3

type ExecutorSpec =
  | { kind: 'notify'; text: string }
  | { kind: 'nomi'; model?: ModelRef; tools: ToolClass[] } // tools 含 'delegate' 时可委派授权里的 clis（§7.3）
  | { kind: 'cli'; cli: DelegateCli; model?: ModelRef; cwd: string; isolation: 'worktree' | 'shared' };

interface Attempt {
  id: string;
  taskId: string;
  gen: number; // 单调递增；晚到结果按 gen 丢弃
  cause: { kind: 'manual' | 'schedule' | 'event' | 'retry' | 'resume'; eventKey?: string };
  snapshot: ExecutionSnapshot; // 固定这次执行用的 CLI、供应商、模型、工作区、授权版本
  status: AttemptStatus;
  startedAt?: number;
  endedAt?: number;
  usage: { inputTokens: number; outputTokens: number; costUsd?: number; costKnown: boolean };
  result?: { summary: string; artifacts: ArtifactRef[]; checks?: CheckResult[] };
  error?: { code: string; message: string };
  carrier?: { tabId?: string; sessionId?: string }; // 执行载体（编程助手标签），不是任务身份
}

interface ExecutionSnapshot {
  grantVersion: number;
  providerId?: string; // 只存引用，不存密钥
  endpoint?: string;
  model?: string;
  cli?: DelegateCli;
  cwd?: string;
  worktree?: string;
}
```

### 4.3 存储

- 目录：`userData/tasks/`，每个任务一个 `<taskId>.json`（任务 + 授权 + 最近若干次执行的摘要），用 `utils/privateFile`
  原子写入；每个任务另有 `<taskId>.events.jsonl` 只追加的事件日志（状态变化、副作用日志、投递记录），也是审计记录。
- 规模预期：几十到几百个任务。启动时只读 `*.json`；事件日志按需读。超过 N 条的历史执行归档压缩（N 待定）。
- Node 与 Go 读写同一格式（Go 版从 Electron 版迁移用户数据时一并迁移，见 `internal/migrate`）。

## 5. 状态机

### 5.1 任务状态

| 状态              | 含义                                                   | 在收件箱   |
| ----------------- | ------------------------------------------------------ | ---------- |
| `idle`            | 等触发（定时 / 事件）                                  | 否         |
| `queued`          | 已触发，等并发名额                                     | 否         |
| `running`         | 有一次执行在跑                                         | 否         |
| `waiting_user`    | 执行停下来等用户：要确认的动作、要补充的信息、预算用完 | **是**     |
| `needs_reconcile` | 重启后不确定外部动作有没有生效，需要核对（§10）        | **是**     |
| `awaiting_accept` | 执行者说做完了，等用户验收（`acceptance: 'user'`）     | **是**     |
| `done`            | 一次性任务完成并通过验收                               | 否         |
| `failed`          | 重试用完或不可重试的错误                               | 是（可关） |
| `cancelled`       | 用户取消                                               | 否         |
| `expired`         | 授权到期                                               | 是（可关） |

重复任务每次执行结束回到 `idle`；一次性任务结束到 `done` / `failed`。

### 5.2 转换（节选）

| 从                | 事件                                     | 到                                               |
| ----------------- | ---------------------------------------- | ------------------------------------------------ |
| `idle`            | 触发（且授权有效、预算未用完、未在冷却） | `queued`                                         |
| `queued`          | 拿到并发名额                             | `running`（新建 Attempt，`gen + 1`）             |
| `running`         | 需要确认 / 需要信息 / 预算用完           | `waiting_user`                                   |
| `waiting_user`    | 用户批准 / 补充                          | `running`（同一 Attempt 继续）                   |
| `running`         | 执行者报告完成                           | `awaiting_accept` 或 `done` / `idle`             |
| `awaiting_accept` | 用户接受 / 退回（附意见）                | `done` / `queued`（新 Attempt，带意见）          |
| `running`         | 失败且可重试（瞬时错误，最多重试一次）   | `queued`（退避）                                 |
| `running`         | 应用退出                                 | 启动时按 §10 核对 → `queued` / `needs_reconcile` |
| 任意未结束状态    | 用户取消                                 | `cancelled`（停止执行，保留成果）                |
| 任意              | 授权撤销 / 到期                          | `waiting_user`（要求重新授权）/ `expired`        |

状态转换写成纯函数 `transition(task, attempt, event) → { task, attempt, effects[] }`，Node 与 Go 各实现一份，用 parity
golden 比对（§15）。副作用（启动执行、发通知、停止进程）由外层根据 `effects` 执行，便于测试。

失败用稳定的错误码（`TaskErrorCode`）表示，Node 与 Go 共用一张表；每个码标明是否可重试、给用户的处理建议。
可重试的只有瞬时错误（HTTP 408 / 429 / 5xx，连接被拒、重置、超时，编程助手进程意外退出）；最多 3 次，退避 2 秒起翻倍、
封顶 60 秒。配置变化（§8.7）、授权问题、执行超时（`timed_out`）、执行者报告失败不重试。重复任务**连续失败 3 次自动暂停**
并进收件箱，成功一次清零（`consecutiveFailures`）。依据见 [参考与取舍](persistent-tasks-references.md) §2.3、§2.4。

### 5.3 代次与晚到结果

- 每个 Attempt 有 `gen`；执行者回报时带上 `gen`。任务当前 `gen` 已前进（取消、接管、重试）时，晚到的结果、审批应答、
  worktree 回填一律丢弃并记日志，不会让已取消的任务复活，也不会写进另一个对话。
- 用户接管编程助手标签：Attempt 标为 `taken_over`，任务进 `waiting_user`（「你已接管，做完后告诉我是否算完成」）。

### 5.4 完成要人确认

执行者说「做完了」不等于任务完成。`acceptance: 'user'`（编程助手任务、写入类任务默认）时进 `awaiting_accept`，卡片上给出
Diff、跑过的命令、检查结果；用户接受才算完成。检查失败、超时、缺依赖分别显示，不用「已完成」代替验收。

## 6. 触发器与事件源

### 6.1 事件源插件接口

GitHub 只是事件源之一。事件源是插件化的，统一接口：

```ts
interface EventSource {
  id: string; // 'folder' | 'web' | 'github' | 'mcp:<server>/<tool>' | 'app' …
  /** 用户可读的说明与需要的授权（创建任务时展示） */
  describe(filter: unknown): { title: string; needs: GrantScope[] };
  validateFilter(filter: unknown): Result;
  /** 拉一次：返回新事件和新游标；游标持久化在任务里 */
  poll(filter: unknown, cursor: string | null, ctx: SourceContext): Promise<{ events: SourceEvent[]; cursor: string }>;
  /** 可选：本机推送型（文件系统监视、应用内部事件），不经网络端口 */
  watch?(filter: unknown, emit: (e: SourceEvent) => void): Disposable;
  minIntervalMs: number;
}

interface SourceEvent {
  key: string; // 去重键：来源内唯一且稳定，如 'github:owner/repo#219:comment:123'
  occurredAt: number;
  summary: string; // 给用户看
  payload: unknown; // 给执行者；一律视为外部内容（§8.3）
}
```

### 6.2 内置事件源（分批）

| 事件源   | 方式                                                  | 用例                                                 | 期  |
| -------- | ----------------------------------------------------- | ---------------------------------------------------- | --- |
| `app`    | 应用内部事件（watch）                                 | 编程助手会话结束、下载完成、知识库更新               | 3   |
| `folder` | 文件系统监视（watch）+ 轮询兜底                       | 新文件、文件变化                                     | 3   |
| `web`    | HTTP 轮询（ETag / 内容哈希）                          | 网页、RSS / Atom、JSON 接口变化                      | 3   |
| `github` | REST 轮询（`since` / ETag）                           | issue / PR / 评论 / CI 状态                          | 3   |
| `mcp`    | 定时调用用户指定的 MCP 工具，或订阅 MCP resource 更新 | 邮件、日历、飞书、Jira…… 由用户已装的 MCP 服务器提供 | 4   |

`mcp` 事件源让「接哪些外部系统」不需要我们逐个写：用户装了邮件或飞书的 MCP 服务器，就能把它当事件源用。

### 6.3 去重、乱序、冷却

- 每个任务记最近 500 个已处理的 `key`（以及事件源游标）；同一 `key` 不重复开执行；对应的执行失败时释放该 `key`，下次还能触发。
- 事件按 `occurredAt` 排序后处理；比游标旧的迟到事件丢弃或合并（按事件源规则）。
- `cooldownMs`：**批处理**语义——第一个事件开窗口，窗口结束或攒满 `maxBatch`（默认 20）就开一次执行，带上窗口内全部事件；
  不用「只取最后一个」的防抖，因为一串评论每条都要处理。
- **重叠**：定时到点时任务还在执行 → 跳过本次并记一条「上次还在跑」（同 Temporal Schedules 默认的 Skip）；
  事件触发时还在执行 → 合并进下一次（见下一条）。
- 执行进行中来了新事件：默认排队合并（下一次执行一起处理），不打断当前执行。
- **只记录模式**：事件触发器有 `mode`。新建的事件任务默认 `observe`：命中的事件只记进任务（收件箱显示「发现 N 件事，
  要不要处理」），不开执行；用户在任务详情里改成 `act` 才自动执行。改成 `act` 是放宽授权，走 `tasks.grant`。

### 6.4 在线与网络

- 只用**出站轮询**和本机监视，不开放本机端口接收 webhook。轮询间隔不低于事件源的 `minIntervalMs`，并遵守对方的限流头。
- 事件源和对外动作都经**连接**（[connections.md](connections.md)）：任务里只存连接 id，凭据留在钥匙串或原软件里，
  执行者看不到令牌。GitHub **可以复用本机 `gh` 登录**，也可以粘贴细粒度令牌；复用时的权限收窄与子进程隔离见
  connections.md §4。
- 所有出站请求走 `netGuard`，与其他功能一致。

## 7. 执行者

| 执行者   | 做什么                                       | 复用                                                      |
| -------- | -------------------------------------------- | --------------------------------------------------------- |
| `notify` | 发一条通知 / 气泡                            | `DesktopService.notify`、提醒                             |
| `nomi`   | 无界面跑一轮 Nomi agent 循环，工具按授权裁剪 | Nomi 对话的工具层与网关；需新增「无界面执行」入口（§7.1） |
| `cli`    | 后台编程助手标签执行目标                     | `DelegateService`：worktree 隔离、审批、接管、并发上限    |

### 7.1 Nomi 无界面执行

现在 Nomi 的 agent 循环挂在对话窗口的一轮上。新增 `runNomiTask(attempt)`：

- 构造 system prompt：任务目标 + 本次事件摘要 + 上次执行的结论（任务的「工作记忆」，存在任务里，有长度上限）；
- 工具集 = 授权允许的工具类 ∩ Nomi 工具；工具调用经同一个 `PermissionBroker`，但处于**后台模式**（§8.4）；
- **可以调用用户在 Nomi 里装好、配好的编程助手**（§7.3）：授权里列出的 CLI 以 `delegate_to_cli` /
  `delegate_followup` / `delegate_stop` 的形式出现在工具集里，Nomi 把子任务交给它们，结果回到这次执行；
- 输出：总结 + 可选的结构化结果（`task_report` 工具，类似委派的 `parseDelegateReport`）；
- 运行轨迹存为一个只读的「任务会话」，在任务详情里可看，不出现在普通对话列表。

### 7.2 编程助手

复用委派：新建后台标签、worktree 隔离、子任务权限不宽于授权。不同点：

- 任务身份是 `taskId`，标签只是本次执行的载体（`Attempt.carrier`）；
- 并发上限（现为 `MAX_PARALLEL_DELEGATES = 3`）对首次执行、重试、恢复、followup 一视同仁；超出时排队（`queued`），不再拒绝；
- 执行停下来等人（`waiting_user`）时**释放名额**；用户回应后走预留的一个「人工名额」恢复，新工作挡不住人推进已有工作；
- 执行结束后 worktree 保留到用户验收，回填（apply 到主工作区）是用户在验收卡片上的单独动作。

### 7.3 Nomi 打底，编程助手按场景优先

**Nomi 自己必须能完成任务需要的全部能力**——读写文件、在 worktree 里改代码、跑命令（经命令审核）、联网、
知识库与记忆、经连接的对外动作。这是底线：用户一个编程助手都没装，任何任务也照样能做。

在此之上，**用户在 Nomi 里安装并配置好的编程助手可以按场景优先调用**：既可以作为 `cli` 执行者（用户点名
「让 Claude Code 接着做完」），也可以被 `nomi` 执行者当作工具委派子任务（例如「每周五汇总」由 Nomi 主持，
代码部分交给 Claude Code）。

| 来源                 | 例子                                  | 可用条件                                     | 限制                                                            |
| -------------------- | ------------------------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| 内置编程助手         | Claude Code、Codex、Gemini、Grok、dsh | 已安装，且已登录官方账号或配了第三方供应商   | —                                                               |
| 外部 CLI（ACP 接入） | 用户在设置里加的任意 ACP CLI          | 用户已添加，启动检查通过（缺的环境变量补齐） | 不经网关：用量按 CLI 上报或「未知」，预算只按时长；没有额度监视 |

- **按场景的优先顺序**：每个场景（编程开发 / 需求文档 / 代码审查 / 调研，沿用委派的任务类型）有一个优先列表，
  默认 = 设置里该类型的默认编程助手 → 编程开发的默认 → **Nomi 自己**；Nomi 永远在列表末尾兜底。
  执行时取列表里第一个可用的。授权里的 `clis` 列出这个任务**允许用**的编程助手，不在列表里的一律不用。
- **用户点名的不悄悄换**：任务是「让 Claude Code 做」（`cli` 执行者，钉住）时，执行时它不可用（卸载、登出、
  换了账号）→ 停下来问（`waiting_user`），选项是「换成 Nomi 自己做」或「等我修好」，不自己换（§8.7）。
- **按优先级选的如实说明**：没钉住时，优先的不可用就顺延到下一个（最终是 Nomi 自己），执行快照记下实际用的是谁，
  结果卡片写明「这次由 Nomi 完成：Claude Code 未登录」。
- **权限按授权等级换算**：L1 → 计划档（只读）；L2 → 在 worktree 里改文件（acceptEdits）；L3 → 可以跑命令
  （仍经命令审核）。永远不给「完全放开」，也不比用户给该 CLI 设的默认档更宽（同委派 §5）。
- **深度一层**：被委派的编程助手不能再委派、不能创建任务（§8.5）；子任务的用量计入本任务预算，并占并发名额。

## 8. 授权（Grant）

### 8.1 原则

- 后台任务**单独授权**，不继承前台的权限模式（即使前台是「全部自动」）。
- 授权由用户在确认卡片上给出；**Nomi 不能给自己授权**，任务内容（包括外部事件）声称「已授权」一律无效。
- 授权有版本号；执行时快照版本，但每个检查点都再查当前是否已撤销（§8.6）。

### 8.2 能力等级

| 等级 | 能力                                                                          | 默认                     |
| ---- | ----------------------------------------------------------------------------- | ------------------------ |
| L0   | 只发通知                                                                      | —                        |
| L1   | 只读：读授权范围内的文件、网页、事件内容、本机会话记录；联网只读              | 新任务默认               |
| L2   | 本机写：写知识库 / 记忆；编程助手在 **worktree** 里改代码                     | 需勾选                   |
| L3   | 跑命令（经命令自动审核，§8.4）                                                | 需勾选                   |
| L4   | 对外的副作用：发评论、建 PR、发消息……逐类勾选（`external:github.comment` 等） | 需逐项勾选               |
| —    | 合并、发布、生产操作                                                          | **永不授予**，每次人决定 |

### 8.3 作用域与期限

授权写明：工作区 / 仓库 / 文件夹范围；允许的事件源与对外目标（以 `ConnectionGrant` 逐项列出连接、能力、资源，
见 [connections.md](connections.md) §2）；执行者与允许调用的编程助手（`clis`，§7.3）；期限（默认 30 天，
到期进 `expired`）；预算（§9）。范围收窄立即生效；放宽需要重新确认。

### 8.4 后台模式下的审批

前台的「确认」是弹卡片；后台没有人在看，规则调整为：

| 情况                             | 前台（2.0.9） | 后台任务                           |
| -------------------------------- | ------------- | ---------------------------------- |
| 低风险命令                       | 直接跑        | 有 L3 授权则直接跑                 |
| 中风险命令，本轮没读过外部内容   | 直接跑        | 有 L3 授权则直接跑                 |
| 中风险命令，读过外部内容         | 要确认        | **暂停 → `waiting_user`**          |
| 高 / 极高风险，或审核失败 / 超时 | 要确认        | **暂停 → `waiting_user`**          |
| 授权外的动作                     | 按权限模式    | 直接拒绝并记录；需要时暂停请求扩权 |

**由事件触发的任务从一开始就算「读过外部内容」**（事件 payload 是外部内容），所以它们的中风险命令一律暂停等人。
这条规则直接复用 2.0.9 的外部内容标记（`markExternalRead`），不另写一套。

### 8.5 防止失控

- 任务内不能创建任务、不能修改自己的授权或预算。
- 委派深度不变：编程助手不能再派任务（同 [nomi-delegate-cli.md](nomi-delegate-cli.md) §6.4）。
- 全局上限：同时运行的任务数、每小时新执行数、每日总费用；超过则排队并提示。

### 8.6 撤销检查点

撤销或暂停任务后，以下位置都要检查并停下：出队前、开始执行前、每次工具调用前、审批应答到达时、重试前、恢复前、
worktree 回填前、对外投递前。

### 8.7 凭据与配置变化

执行快照固定供应商、端点、模型、CLI 账号的**引用**；密钥正文不进任务、提示词、日志。执行时发现引用的配置变了
（供应商被删、Key 换了、账号切了），不悄悄换成别的：本次执行失败并提示，用户确认后用新配置重跑。

## 9. 预算与用量

- 预算维度：每次执行的 token 上限、每次执行的时长上限、每日 / 总费用上限、重试次数上限。默认值待定（§18）。
- 用量归属：网关记账时带上 `taskId` / `attemptId`（Nomi 执行经网关；编程助手第三方经网关，官方账号按 CLI 上报的用量）。
- 费用未知（官方订阅、无价格表）时显示「未知」，预算只按 token 与时长判断，不编造费用。
- 预算用完：当前执行停在 `waiting_user`（「预算用完，继续需要你批准」），不直接判失败。
- 用量页按任务分组显示；任务详情显示每次执行的用量。

## 10. 副作用日志与重启恢复

### 10.1 副作用分类

每个工具声明影响范围：

| 范围       | 例子                                           | 重启后                   |
| ---------- | ---------------------------------------------- | ------------------------ |
| `none`     | 读文件、搜网页、读事件                         | 可以重做                 |
| `local`    | 写 worktree、写知识库、写记忆                  | 可以重做（幂等或覆盖写） |
| `external` | 发评论、建 PR、发消息、调用有副作用的 MCP 工具 | 不可盲目重做，需核对     |

MCP 工具默认按 `external` 处理，除非用户把某个工具标为只读。

### 10.2 先记意图，再做动作

`external` 动作执行前先往事件日志写 `intent`（含幂等键 `taskId:attemptId:seq` 与内容哈希），成功后写 `done`（含外部 id，如评论 id）。
取消是协作式的：取消后才到达的 `intent` / `done` 照常记日志（审计完整），只是结果不再投递。

### 10.3 启动时核对

| 上次执行的情况             | 处理                                                                              |
| -------------------------- | --------------------------------------------------------------------------------- |
| 没有 `external` 动作       | 自动重新排队（新 Attempt，带上次的进度摘要）                                      |
| `external` 动作都有 `done` | 从下一步继续（新 Attempt，告知已完成的动作）                                      |
| 有 `intent` 没 `done`      | `needs_reconcile`：能查询的事件源先自动查（这条评论发出去没有）；查不了就交给用户 |
| 编程助手执行中断           | worktree 保留；重新排队时在同一 worktree 继续，并告知中断位置                     |
| 停在 `waiting_user` 等人   | **保持原样**，问题不丢、不重问；用户回答后以 `resume` 新开执行，回答写进恢复说明  |

续跑的执行一律带**恢复说明**：已完成的对外动作、中断位置，以及「重复任何对外动作前先核对目录、git 历史和远端」。
MCP 工具返回的长任务句柄（MCP Tasks 扩展）记进事件日志，重启后先继续轮询，查到结果就不必核对。

不承诺对外 exactly-once；承诺的是**不盲目重复**。

### 10.4 退出、休眠、托盘

- 关掉主窗口、应用留在托盘：任务照常运行。
- 应用退出：运行中的执行标为中断，下次启动按 §10.3 核对；错过的定时触发按 `catchUpMs`（默认沿用现在的 12 小时）补跑一次。
- 系统休眠：唤醒后同上。可选「任务运行时阻止系统休眠」（默认关）。
- 界面如实显示「应用关闭期间已暂停」，不假装一直在跑。

## 11. 投递与收件箱

- **Outbox**：结果、请求都先写入 outbox，再发送；发送成功写确认。重启后重发未确认的，按 id 去重，**重发不会重新执行任务**。
  失败重试 2 秒起翻倍、封顶 1 分钟；连续失败 3 次才显示为问题；同一任务发往同一目标的消息保序；丢弃的消息留档（原因、时间）。
- 投递目标：任务详情（总在）、来源对话（若还在；被删除就只留在任务详情，不新建对话）、系统通知、诺米的气泡。
- 只在**有结果、需要人、出错**时通知；遵守免打扰时段（复用 `SchedulerService` 的设置），免打扰期间积累，结束后合并成一条。
- 不在免打扰时段也合并：同一个短时间窗（默认 30 秒）里到达的多条投递合并成一条（「3 个任务有结果」），避免连续刷屏。
- **收件箱**：所有 `waiting_user` / `needs_reconcile` / `awaiting_accept` 的任务集中显示，每条带一个明确的动作按钮
  （批准、补充、验收、核对）。

## 12. 界面

- **入口**：侧栏会话列表上方，与素材库并列：「任务」，带收件箱角标。
- **任务列表**：按状态分组（需要你 / 运行中 / 等触发 / 已结束）；每项显示触发方式、下次运行、最近结果、本月用量。
- **任务详情**：目标、触发器、授权（可收窄、撤销）、预算、执行历史；每次执行可展开轨迹（Nomi 执行的只读会话，
  或编程助手标签——复用 2.0.9 的子任务抽屉）。
- **创建**：
  1. 在对话里说「每天 9 点帮我看看……」，Nomi 用 `task_propose` 工具起草，弹出**授权卡片**（目标、触发、执行者、
     能力等级、范围、期限、预算），用户确认后才创建；
  2. 任务页手动新建（表单）。
- **已有入口迁移**：设置里的「定时任务」「提醒」改为指向任务页对应的过滤视图。
- 文案中文为 key，英文进 `en.json`；卡片用现有 `ConfirmDialog` / 卡片组件；遵守样式与无障碍约定。

**2.1.0 的实施调整（2026-11-01）**：上表的数据迁移推迟到任务系统稳定之后的版本。原因：提醒与定时代理任务各自
牵连 Nomi 工具（`reminder_*`）、桌面角色的到点事件（稍后提醒 / 关闭）、`desktop.reminders*` / `sched.*` 契约与 Go 版的
parity 用例，迁移等于在两个版本里重写两套已稳定的引擎，回归风险大而用户得不到新能力。2.1.0 的做法：

- 需要工具、预算、授权的新需求一律建成任务；对话里说「每天 9 点帮我看看……」由 `task_propose` 起草任务，
  只是「到点提醒我」仍走提醒；
- `notify` 执行者照常实现，供新建的纯通知任务使用。

## 14. 契约（草案）

新增域 `tasks`（`packages/contract/src/app/tasks.ts`，处理函数 `core/src/contract/tasks.ts`，Go 对应 `internal/core/taskshandlers`）：

| 过程                                            | 说明                                        | dangerous        |
| ----------------------------------------------- | ------------------------------------------- | ---------------- |
| `tasks.list` / `tasks.get`                      | 列表 / 详情（含执行摘要）                   | 否               |
| `tasks.inbox`                                   | 需要用户处理的任务                          | 否               |
| `tasks.create`                                  | 用户在表单或授权卡片上确认后创建            | **是**           |
| `tasks.update`                                  | 改标题、触发器、预算；收窄授权              | 否               |
| `tasks.grant`                                   | 放宽授权 / 续期                             | **是**           |
| `tasks.revoke` / `tasks.pause` / `tasks.resume` | 撤销 / 暂停 / 恢复                          | 否               |
| `tasks.cancel`                                  | 取消（停执行、保留成果）                    | 否               |
| `tasks.runNow`                                  | 立即执行一次                                | 否               |
| `tasks.decide`                                  | 回应 `waiting_user`（批准、拒绝、补充）     | **是**（批准时） |
| `tasks.accept` / `tasks.reject`                 | 验收 / 退回                                 | 否               |
| `tasks.reconcile`                               | 核对结果：已生效 / 未生效 / 放弃            | 否               |
| `tasks.applyWorktree`                           | 把 worktree 的改动回填到主工作区            | **是**           |
| 事件 `tasks.changed`                            | 任务或执行状态变化（`eventSurfaces: chat`） | —                |

Nomi 工具：

- `task_propose`：起草，只产生授权卡片，不直接创建；
- `task_report`：执行者回报结果，仅在任务执行中可用；
- `task_recall(id)`：只读，返回任务摘要、最近一次执行的结论和关联对象的 id（来源对话、Attempt、连接），
  模型可以按 id 逐跳查下去；结果有长度上限，不含任何密钥；
- `delegate_stop(taskId)`：停止一个后台委派，等同 `tasks.cancel`（与 `delegate_to_cli` / `delegate_followup` 成对）。

## 19. 风险

- **范围膨胀**：任务系统容易长成工作流引擎。坚持 §1 的「不做」，新需求先问能否用现有触发器 + 执行者组合表达。
- **后台消耗**：无人值守的模型调用会花钱。预算默认值偏保守，用量页可见，超额一律暂停等人。
- **提示注入**：事件内容是攻击面。外部内容标记 + 后台审批规则 + 对外动作逐类授权三层兜底。
- **双版本工作量**：状态机纯函数 + parity golden 控制两边一致的成本；执行者复用现有模块。
