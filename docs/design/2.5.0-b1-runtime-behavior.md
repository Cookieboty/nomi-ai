# 2.5.0 B1：会话级运行时行为切片（fake 驱动，不接生产）

## 已交付的行为，不是仅接口草案

`Session` 为一个固定 `ConversationID` 串行管理产品转录、native bindings、active attempt 和 generation。`Runtime` 自己拥有 loop/tools，Session 只做一次 recover + 一次 start 和事件接收，不把 CLI 工具搬回另一个 Nomi loop。

- **真实内存流程**：fake Claude 新建 + full → fake Codex 新建 + full → 切回 Claude 的原 native binding + delta。产品会话 id/消息 id 不变，自己的最终 assistant 正文经 `ConfirmNative` 记录，切回不会重传自己的回答。
- **恢复先于规划**：Runtime 回答 `resumed / new / fallback / unknown / error`。只有 exact compatible binding + 相同 native ID 的 resumed 才允许 delta。尝试恢复却报 new、resumed 却换 native ID、缺 identity 都拒绝；显式 fallback 重新做 bounded full，绝不沿用 old coverage。
- **不提前 ACK**：Recover 成功、Start 返回 submitted 都不是交付证明。只有 active token + actual target native ID + matching plan 的 typed delivery 回执才能提交 coverage。错误目标的 full/unknown/pre-submit 回执不改变审批或状态。partial/unknown 交付可以有已证明的部分覆盖，但结果转 uncertain，不能自动补发用户副作用。
- **事件围栏**：每条事件带 `(conversationId, attemptId, generation, nativeSessionId)`。取消在调用 Runtime.Cancel **之前**递增 generation、撤销旧审批所有权并取消 context。旧 text/delivery/completion/approval/activity/failure 及迟到方法结果不能再写转录、coverage 或审批。
- **取消不是回滚副作用**：只有 stopped 且已证明 running/queue/approval/background/subagent 全为零才解除阻塞。超时、unsupported、unknown、残留后台均 uncertain；不能自动重试。Recover/Start/Approve/Cancel 按 attempt gate 排序，确认 stop 之后不会有排在它后面的旧 Start。取消遇到阻塞 Recover/Start 时，迟到返回不能重新发起用户 turn。
- **审批**：只路由当前 generation 的显式 allow/deny；deny 不变 allow。未支持审批的 native 请求转 uncertain，不自动回答。取消会使正在返回的审批结果失效；同一审批不会因为并发点击执行两次。
- **空闲门控**：preparing、running、canceling、uncertain、产品 FIFO 队列、未决审批、native queue/background/subagent 或 activity unknown 都拒绝切换/新发送。完成后若仍有后台工作，只有本 generation 的明确 quiescence 事件或 confirmed stop 才能解锁。
- **排队不自动执行**：Enqueue + StartNext 是显式 FIFO；完成不会自动跑下一项。DropQueued 是显式移除。相同 logical request 的并发 Start 只发一次；重复 completion 只写一个 assistant。
- **权限/能力**：有效产品权限只认 ask/deny/bypass，必须在 native 能力中列出；bypass 另需显式确认，未知 native 字符串不能发明产品权限。无 resume 能力直接 new/full 并保留旧绑定；产品附件桥接未实现，能力显式降级且带附件的输入拒绝，不静默删除。MCP/skills/memory 不会因为换 Runtime 自动共享。

## 本轮审查修复的具体问题

1. 旧 planner 把 current entry 的 Order 隐式当作历史 cutoff：重试一个较早失败请求会静默丢掉期间产生的有效历史。现在普通重试只排除当前逻辑 ID；显式新分支视图才用 `HistoryBeforeOrder`，并拒绝对已有 native resume 偷套 cutoff。原 cutoff 测试仍验证相同排除结果，只是把意图变为显式输入；新增跨 turn 的失败重试证明较新历史仍被 full 携带。
2. native ID 必须按 compatibility key 命名空间隔离：Claude/Codex 或不同账号都可能使用同一个 native 字符串。不能全局按裸 native ID 判冲突。
3. fallback 后多个历史 binding 同 key 时，要优先最近**确认交付**的 binding；不能恢复后提前推进偏好，更不能清空旧 binding。
4. 内部生成 reply ID 不能撞上导入的既有消息或排队的用户 ID；选取未占用 ID，不覆盖旧消息。
5. completed 记录按逻辑 ID + revision 防重复执行。编辑的新修订必须显式 Retry 才可发送，stale native 不复用；相同已完成修订连 Retry 也不能重复执行。
6. 非法 UTF-8 的身份/恢复敏感字段必须拒绝，避免不同 cwd/account/config 在 JSON 替换字符时别名成同一个 compatibility key。
7. native 报 stopped 但后台不为零仍 uncertain；反过来，已完成且明确 idle 的 Cancel 是无副作用幂等 no-op，不能破坏可续接 binding。

## 明确未交付

- 所有代码仅内存 + fake。没有真实进程、登录/凭据、模型/API 调用、生产 UI/IPC 改动或真实 userData 迁移。
- generation、attempt、queue、binding preference、转录和 receipt 尚未持久化；这不是 crash-safe 生产事务。`NewSession` 的初始 history 只用于简单 fixture，拒绝修订版快照以避免悄悄降为 revision 1，不能拿它当作恢复入口。
- 流式正文先保存在当前 attempt 的 draft，只有有效完成才形成最终 assistant 条目；取消/崩溃时的 partial draft 持久化是 B2 的提交状态问题，不声称已解决。
- 活动/交付/stop 证明目前来自 fake 合同；真实驱动必须从官方事件映射，不能伪造回执。实际 adapter 必须支持 bounded context/进程回收，不能靠本内存层强杀一个无视 context 的任意实现。
- API runtime 可实现相同接口，但尚无 API adapter，也未封闭旧持久化 ingress。rewind、durable cancellation、完整用户能力 UI 与真实 providerless 主对话仍未接入。
