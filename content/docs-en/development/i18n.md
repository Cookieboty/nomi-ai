# Internationalization (i18n) Guide

Nomi's localization resources are centralized in the **`@nomi-ai/i18n`** package ([`packages/i18n`](../../packages/i18n)); views, the Go core, and plugins all share the same dictionary. `packages/ui` only retains locale state and view bindings; the Go core embeds a copy (`apps/desktop-go/internal/core/i18n/locales`, verified against the source by `dict_test.go`) and resolves strings via `i18n.T(key, args...)`. At runtime, only stable keys (`project.module.message`) are resolved—**raw Chinese text cannot be used as a key**, and there is no automatic fallback mapping.

## Keys and Directory Layout

Stable keys use three-segment lowercase kebab-case: `project.module.message`.

| Directory | Purpose |
| --- | --- |
| `src/locales/zh` | Baseline Chinese dictionary defining the canonical key set |
| `src/locales/en` | English dictionary |
| `src/locales/<language>` | Additional languages, named with short language codes such as `ja` |
| `src/locales/<language>/<project>` | Project boundary, e.g., `ui`, `electron` (legacy name kept for core/main-process strings), `ai-runtime` |
| `*.json` | Module dictionary, e.g., `chat-settings.json`, `common.json` |

Every key must exist in `zh` and all enabled languages, and interpolation placeholders such as `{0}` or `{name}` must match across languages. Within the same project, two keys must not share identical baseline text, preventing ambiguity during maintenance and translation checks.

Dictionaries hold UI copy only. Prompts sent to models do not belong in dictionaries; they live in `internal/core/prompts/text` in the Go core (see `apps/desktop-go/README.md`).

Application code always references stable keys:

```ts
t('ui.chat-settings.new-chat');
t('electron.common.read-failed', fileName);
```

## Workflow for Changes

1. Add or update the key in the same module across `zh` and all other languages.
2. Run `node scripts/i18n/refresh-catalog.mjs` to update the generated `catalog.ts`.
3. If you modified keys also used by Go (such as `electron` or `ai-runtime`), run `pnpm i18n:sync` to sync `packages/i18n/src/locales` byte-for-byte to `apps/desktop-go/internal/core/i18n/locales` (TS is the single source of truth—never copy manually; `pnpm check:i18n` passes `--check` and fails CI on drift).
4. Run `pnpm check:i18n`.
5. Run typecheck and tests for affected packages (Go: `go test ./internal/core/i18n/`).

The check reports: Chinese keys, invalid key formats, missing or extra translations, mismatched placeholders, duplicate baseline text within a project, unknown keys in source code, and dead keys. String literals in Go source and embedded JSON (`apps/desktop-go`, excluding tests) are also counted as usages (`goKeySources`); format strings like `fmt.Sprintf("electron.common.task-level-%d", n)` match a group of keys by pattern; keys under `electron.*` or `ai-runtime.*` referenced in Go but absent from the dictionary are reported as unknown.

## keepZh (Retaining Chinese)

`keepZh` in `scripts/i18n/config.cjs` lists source files that **intentionally retain Chinese text outside the dictionary**. These strings are used for model prompts or internal parsing rather than user-facing UI:

- Wake words (`voice/src/wake.ts`)

Model prompts and tool schemas in the Go core do not go through the dictionary; the checker inspects Go files only for strings shaped like stable keys and ignores Chinese prose inside them.

Do not use `keepZh` to bypass checks for user-facing UI strings; put them in `packages/i18n` and call `t()` / `tr()`. Update this document whenever `keepZh` is modified.
