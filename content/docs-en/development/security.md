# Security Boundaries

For user-facing documentation, see [features/privacy-security.md](../features/privacy-security.md); this page lists the implementation locations—review them before modifying these subsystems.

## Views ⇄ Core

- Views access the core exclusively through the app contract ([contract.md](contract.md)): each window receives a one-time token by which the core identifies the caller's surface; `surfaces` and `dangerous` on each procedure are enforced by the guard in `internal/contract/frames.go`. The WebSocket listens only on `127.0.0.1`.
- Native paths of dropped files are obtained by the host from native drag-and-drop events (`WindowFilesDropped` in `wailsshell`); views cannot submit arbitrary paths.
- Views pass only a project ID (`extra.projectId` for Nomi chat, `projectId` for new tabs), never a directory path: project folders are fetched live by the core from `core/projects`, re-validated against workspace root rules before every use, and treated as absent if unrecognized; any `extra.cwd` supplied by a view is discarded.

## Desktop Capabilities (Nomi's File / Command Tools)

## Agents (CLI Subprocesses)

Agents run as the current user. Nomi enforces the following protections in `internal/core/cli/harness`, regardless of permission mode:

- **Working directory**: `Deps.CwdCheck` (wired to `desktop.PermissionBroker.CheckCliWorkspace`, sharing the same rules as Nomi chat workspaces: must not be overly broad and must not lie inside built-in or user-protected folders). Checked when creating a tab, changing directories, and before every CLI launch (`cwdErr` in `spawn.go`).
- **Additional project folders**: Tabs store only `projectId`; additional folders are fetched live from `core/projects` on every launch (validated against workspace root rules when creating/editing a project, and re-checked on fetch) and passed to the CLI (`--add-dir` / `writableRoots` / `additionalDirectories`), with the same write access as the working directory inside the OS sandbox (read-only in `plan` mode). See [coding-agents.md "Projects"](coding-agents.md#projects).
- **Environment variables**: `CliChildEnv` first runs `cli.ScrubSecretEnv` (`internal/core/cli/envscrub.go`) to strip inherited credential variables (tokens, passwords, cloud access keys, connection strings), except model service credentials and user-allowlisted variables (`Deps.EnvAllow`); variables injected by Nomi itself (tab tokens, official account directories) are preserved. Nomi's `workspace_run` uses the same environment (`desktopShellEnv` in `igtools_wiring.go`).
- **Codex network access**: `codexNetwork` defaults to off, persisted under `codexNetworkAllowed` (true only if explicitly enabled by the user). The approval policy for `acceptEdits` is `on-request`, so out-of-sandbox requests trigger Codex approval prompts routed into the permission queue. (When Nomi's OS sandbox is active, Codex's own sandbox is disabled and this setting has no effect; see below.)

### OS-Level Sandbox (macOS)

**Threat model**: The sandbox defends against agent **accidental misuse** and **prompt-injection exfiltration or corruption** (reading credentials, modifying user configs, writing outside the project). It does not stop a determined malicious process: it is a "default-allow + deny-by-path" blocklist without network restrictions, so everything else a process can do (spawning subprocesses, connecting to remote services) still works. Risk reduction comes from denying reads to sensitive data, scrubbing environment variables, restricting writable locations, and closing the bypass vectors listed below; stronger isolation (containers, VMs) is out of scope here.

`internal/core/cli/sandbox` + `harness/sandbox.go`. Every session process (Claude persistent process, Codex app-server / exec, ACP, per-turn CLI processes) is wrapped with `/usr/bin/sandbox-exec -p <profile>` (`spawnCLI` -> `spawnHarness`), with profiles generated per tab and per launch (`sandbox.Profile`):

- Default allow, with **read-data denied** (`file-read-data`; directory listing and `stat` remain allowed) by category: SSH and Git credentials (including GitHub CLI tokens), cloud account credentials (including `.pypirc` / `.gem/credentials` publish tokens in the home directory), secrets and password vaults (including 1Password CLI's `.config/op`), browser data (Chrome, Firefox, Edge, Brave, Arc, Chromium, Vivaldi, Opera, Safari), personal data (Mail / Messages / Calendar / Contacts / Notes / Photos, plus shell and REPL histories), secret files (`.env*` excluding `.env.example` etc., `*.key`, private `.pem` keys, etc. in the home directory and project), plus user-protected folders and Nomi's own data directory (except `prompt-images` and CLI official account directories). The system Keychain is not blocked: blocking Keychain reads breaks official CLI sign-ins, and items are already protected by macOS access controls. `~/.pypirc` in the home directory is still read-denied, but treated as a routine package manager read (`RoutineRead`) without popping an authorization prompt. `~/.npmrc` is readable but not writable: it often configures registry mirrors, and denying reads causes sandboxed npm to hit the default registry or causes nvm to error on every shell startup; writes remain blocked (`write:config`, since `script-shell`, `node-options`, etc. can execute commands via npm outside the sandbox).
- **Writes** allowed: project directories (except in `plan` mode), temp directories, `/dev`, the CLI's own directories (manifest `host.homeDirs`: `~/.claude`, `~/.codex`, `~/.kimi-code`, `~/.minimax`, `~/.gemini/antigravity-cli`, ..., plus `~/.claude.json*`) and account / third-party private directories pointed to by `host.homeEnv`, package manager and build caches (`~/Library/Caches`, `~/.npm`, `go/pkg`, ...), **tool state** (hidden entries directly under home `~/.*`, `~/.config`, `~/Library/Application Support`, `toolStateHome`: where tools write logs, caches, and state—such as hook scripts writing `~/.ai-usage`—without prompting for authorization), and user-authorized folders/files. Regular directories under home (Documents, Desktop, Downloads, code directories outside the project) require authorization before writing.
  Post-allow denials: unauthorized credential-category folders and top-level home credential files (`~/.ssh`, `~/.aws`, `~/.netrc`, ..., rule `write`, which still trigger authorization prompts); files whose modification executes commands outside the sandbox (rule `write:config`, no authorization prompt): CLI hooks and configs (`execConfigHome` and manifest `host.execConfig`: `~/.claude/settings.json`, `~/.claude/hooks`, `~/.codex/config.toml`, `~/.gemini/settings.json`, `~/.kimi-code/config.toml`, `~/.minimax/config.yaml`, `~/.gemini/antigravity-cli/settings.json`), configs executed by other tools on startup (`homeExecConfig`: `~/.config/git`, Vim/Neovim, tmux, Hammerspoon, yarn/bun/curl configs, direnv, Cursor/Windsurf/Claude Desktop MCP configs, VS Code / Cursor user settings, ...), login-item/autostart directories, executable directories in `PATH`, shell startup scripts, and `~/.gitconfig`; protected folders and Nomi's data directory are denied again last.
- **Local escape vectors**: Unix sockets are not governed by file read/write rules, so outbound connections (`network-outbound` `remote unix-socket`) are blocked explicitly: `ssh-agent` (`/private/var/run/com.apple.launchd.*/Listeners`, `agent.sock`, `S.gpg-agent`) is blocked unless the SSH category is authorized, and `SSH_AUTH_SOCK` is stripped from the environment; Docker's `docker.sock` (Docker Desktop, Colima, OrbStack) is blocked unless the cloud-accounts category is authorized. Apple Events (`appleevent-send`) are always denied so `osascript` cannot drive Terminal or Finder outside the sandbox. Denials for these vectors are logged only.
- Seatbelt cannot be nested (inner `sandbox_apply` fails when outer deny rules exist), so CLIs have their own sandboxes disabled when wrapped: Claude `--settings {"sandbox":{"enabled":false}}`, Codex `dangerFullAccess` / `sandbox_mode="danger-full-access"` (approval policy stays intact), Gemini `GEMINI_SANDBOX=false`, dsh `DSH_PERMISSION_MODE=danger-full-access`. Network access is unrestricted (Seatbelt only filters by IP, and CLIs must reach model services); exfiltration is mitigated via sensitive-read denials and env scrubbing.
- Every denial carries `(with message "nomi-sbx:<token>:<rule>")`. `sandbox.Monitor` reads violations via `log stream --predicate 'sender == "Sandbox" AND eventMessage CONTAINS "nomi-sbx:"'` (readable by unprivileged users, including process, operation, and realpath), matches the token back to the tab, and `sandbox.Classify` maps it to an authorization request: category, write to a folder (minimal scope: the file's parent directory, bounded by the git repo root if inside one, never opening up broad folders like `~/Projects`), write to a specific file (when the parent folder is too broad, such as files directly in home), read of a specific secret file (`.env` etc. are authorized per file rather than opening the whole category), or protected folder (cannot be authorized in chat). Never grantable for writes (`sandbox.NeverGrantable`, no authorization prompt): autostart locations (`~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`), executable directories in `PATH` (`~/.local/bin`, `~/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, `~/go/bin`, `~/.cargo/bin`, `~/.bun/bin`, `~/.deno/bin`), and shell configs (`~/.oh-my-zsh`, `~/.zsh`, fish/zsh config dirs, `~/.zshrc` and other startup scripts, `~/.gitconfig`). When parsing violations, the message must consist strictly of one denial line + one tag line, paths cannot contain control characters, and a mismatched token forged via a filename inside the sandbox is discarded. Denials on Nomi's data directory are logged only. New requests also emit `permission-needed` (triggering a desktop character bubble and system notification when `background` is true).
- Pending requests sit on tab state `sandboxPending` (not persisted; each item is queued only once) and are shown on the agent tab, delegation card, and task details. `harness.sandboxReply` handles responses: allow for this session (in tab memory), always allow (desktop setting `cliSandboxAllow`: each entry carries `project` = realpath of the working directory's git root, scoped solely to that project, matched by realpath so symlinked working directories cannot borrow another project's grants; validated on both load and insertion for valid category, absolute path, non-broad folder, and non-never-grantable path), or deny (do not ask again in this session). After allowing, `recycleTab` retires the tab's old CLI process (waiting for the current turn if running); the next user message launches a new process with updated permissions and resumes the session. Granting permission only updates permissions—it does not send "please continue" on the user's behalf or auto-start a new turn, and a stopped session will not resume solely because a grant was approved.
- Task pre-authorization: task-authorized `grant.sandbox` (category IDs), automatically including `ssh` when GitHub outbound capabilities are present (`tasks.SandboxGrants`), are written into `delegation.sandboxGrants` on tab creation and treated as already granted in `grantedFor`. Only the core's internal delegation/task paths may set `delegation`: the `harness.tabCreate` contract procedure accepts only view-provided fields (`backend`, `cwd`, `title`, `messages`, `permissionMode`) and discards internal fields such as `delegation`.
- Informing the agent it is sandboxed (`prompts/text/cli-sandbox.md`): Claude receives it via `--append-system-prompt`, while other CLIs receive it prepended to the first message of the CLI session (`withSandboxNote`). If blocked, the agent should stop, explain, and end the turn rather than working around it. The note also states that the CLI's own config directories (skills, prompts, plugins) and `~/.agents` are readable and executable, and that "Permission denied" / exit code 126 when running a script indicates a missing executable bit rather than a sandbox block (sandbox blocks produce "Operation not permitted"), so the agent should invoke the script via an interpreter and continue instead of stopping (`internal/core/cli/sandbox/skills_test.go` guards the skill directories of every built-in CLI).
- Policy changes: toggling `cliSandboxOff` (sandbox enabled by default), protected folders, or "always allow" entries triggers `watchSandboxPolicy` -> `SandboxPolicyChanged`, restarting idle persistent CLIs with the updated profile.
- On other platforms, `sandbox.Supported()` is false and CLIs run as before (status `unsupported`, surfaced in the UI); working directory checks and environment scrubbing still apply. **When no OS sandbox is available, normal (non-delegated) L3 background tasks do not switch to `auto`**: the agent permission mode stays at `acceptEdits` (file edits proceed automatically, commands still require confirmation), and both "risk-based auto-approval" and foreground "auto-approve all" continue prompting per command (never silently carry over macOS auto-execution to Windows/Linux). For **subagents delegated from Nomi chat**, both synchronous and background delegations use `DelegatePermissionMode(cli)`—the highest mode supported by that CLI (typically `bypass`)—and the approval confirmation card must explicitly display the actual permission mode along with the active host protections (OS sandbox on/off/unsupported, working directory validation, and env scrubbing).

## Code Execution Sandbox

`apps/desktop-go/internal/core/sandbox`:

| Language / Platform | Isolation | Fallback |
| --- | --- | --- |
| JavaScript | Native `node --permission`, read/write restricted to temp dir, code-generation-from-strings disabled, memory-capped | — |
| Python · macOS | `sandbox-exec` + built-in Seatbelt profile (writes restricted to temp dir, network disabled by default) | Binary not found -> bare `python -I` |
| Python · Linux | `bwrap` (read-only system dirs, writable temp dir, `--unshare-net`) | `bubblewrap` not installed -> bare `python -I` |
| Python · Windows | No filesystem isolation | — |

The `sandbox` field in the result indicates which isolation mode actually ran, and the UI surfaces it accordingly; stricter confirmation is required when isolation is absent.

## Delegation Working Directory

When Nomi delegates tasks to an agent via `delegate_to_cli` (or persistent task agent execution) (`internal/core/cli/delegate/`):

1. By default, edits run `in-place` in the working directory without creating a worktree. Parallel tasks in the same git repository register which files they are modifying (`claims.go`, derived from file-editing tool event inputs). When two tasks touch the same file, priority arbitrates (`urgent > high > medium > low`, first-come wins on ties): the yielding task receives a steer message telling it not to touch that file again; at wrap-up, the file counts toward the winning task, and files edited by concurrent tasks are excluded from one's own change list. Files modified via shell commands cannot be attributed from tool args, so unclaimed files listed by git still count as the task's own.
2. A detached worktree under `<cwd>/.nomi-delegate/<id>` is created only when a distinct `base_branch` not in the current branch's history is explicitly specified (`.nomi-delegate/` is added to the repo's `info/exclude`).
3. Landing a worktree (`LandWorktree`): small changes (<= 10 files and <= 400 lines) are copied back to the active working tree, skipping target files that already have uncommitted changes or lie outside authorized scope; larger changes or uncopiable files are committed to a new branch `nomi/<base>-<id>` (no hooks, no signing) for the user to decide whether to merge. Commits made directly by the agent that are not referenced by any branch or tag (a clean `git status` does not mean no work was done) also get a branch created to preserve them. The worktree is removed after landing; if preserving fails (inspection or branch creation error), the worktree is kept and an error is reported. Synchronous delegations land immediately upon completion; persistent tasks land via "Land Changes" on the acceptance card or automatically when accepted.
4. On cancellation, failure/abandonment, expiration, or task deletion, the worktree is removed (except for tabs taken over by the user). On app startup, unclaimed delegation worktrees are cleaned up: uncommitted changes are committed to a new branch and unreferenced commits receive a branch before removal; if that fails, the worktree is preserved.
5. Non-git directories run in-place, and the result warns that parallel tasks may overwrite each other's files.
6. The combined concurrency limit for active delegations and background tasks is governed by the Agent Board's scheduling policy (Eco: 5 / Balanced: 10 / Full Speed: resource-gated; defaults to 3 delegations via `MaxParallelDelegates` if the board is not initialized).

Each agent's built-in sandbox (such as Codex's Seatbelt) still applies normally; this layer solely prevents concurrent writes to the same working tree.

Delegated agent tabs are visible only inside Nomi (subtask cards in chat, the subtask drawer beside chat, and the Tasks page): they do not appear in the sidebar, and their sessions do not appear in the agent's history (`harness/orchestrator_delegated.go`). Identical delegations in the same conversation (matching agents, directory, task type, model, and thinking depth) reuse the previous idle session (if used within the last hour, `reuse.go`) to save tokens and startup time; worktree delegations are never reused. Delegated tabs whose associated tasks have finished and that have been idle for over a week are closed on app startup (since users cannot close them from the sidebar).

## Network

- Outbound URLs allow only public `http(s)` endpoints, rejecting embedded credentials and reserved addresses (`internal/core/security/netguard.go`). Gateway outbound traffic also enforces address classification and DNS IP pinning (`internal/gateway/net`) to prevent post-resolution DNS rebinding to private networks.
- Both the gateway and contract servers listen strictly on loopback addresses and validate the `Host` header.

## Secrets and Privacy

- Secrets such as API keys: a master key is stored in the OS keychain and encrypted `enc:` values are persisted on disk (`internal/core/security/secretbox.go`); if the keychain is unavailable, it fails closed rather than falling back to plaintext.
- Privacy mode: the gateway substitutes secrets, tokens, and other sensitive strings with placeholders before sending requests upstream and restores them in responses (`internal/gateway/privacy`).
- Diagnostic logs and audit records are redacted before writing (`internal/core/services/redact.go`, `audit_log.go`).
